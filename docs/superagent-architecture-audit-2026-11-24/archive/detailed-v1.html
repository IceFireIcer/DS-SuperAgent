02 / Architecture
当前拓扑

One surface, three worlds, six boundaries一张图看懂
谁在说话，谁在写事实。

入口不是“某个 Session 收到的消息”，而是版本化来源事件与人类对话。新请求进入 Main； 已拥有 Thread 的后续直接扇出到 Ticket；结果必须经过 Worker 的 ready report、Main 的用户语言和 Router 的 Delivery， 不再允许 Worker 自己决定对外口径。

BOUNDARY 01 / HUMAN ENTRY Main 是唯一的人类连续层

外部新请求先进入 Main；只有已经归属某个 Worker 的 Thread 后续才直接 fan-out。连续对话与执行 transcript 被有意分开。
main-conversation.ts:20 · engine.ts:543

BOUNDARY 02 / WRITE AUTHORITY Ticket 才是业务单位，Session 只是实现细节

Ticket 可跨多个 Assignment；每个 Assignment 有 generation、Session、Environment。迟到的 job / subagent 回调只能唤醒产生它的那一代。
work-delegation.ts:38 · execution.ts:61

BOUNDARY 03 / DELIVERY 统一出口不属于 Worker

Worker 只提交带验证证据的 ready report；Main 生成用户可见文字；Router 的 deliver_result 通过 Delivery/Outbox 发出。
work-delegation.ts:115 · execution.ts:749

BOUNDARY 04 / TOOLS “Router 不执行”不再是提示词愿望

每个 DSH Session 先清空默认工具白名单，再按 Main / Router / Worker 注册本次可用工具。Main 与 Router 没有文件、Shell 执行权。
native-sessions.ts:306

BOUNDARY 05 / WORLDS 本地与远端是显式 Execution Environment

选择 local-only、remote-only、auto 后，绑定不会静默换世界；远端设备用 X25519 / Ed25519 / AES-GCM 固定身份与加密请求。
remote-environment.ts:208 · remote-protocol.ts:120

BOUNDARY 06 / RECOVERY 主机替换是领域事务，不是重启脚本

Host lease + epoch + takeover pending 先阻止新写，再逐票核对设备范围、外部 Effect、人工停止和当前问题；旧进程复活也被 token fence。

约 35% 证据强度

为什么不是更高？

文章要求的不是“模块存在”，而是连续、全双工、主动、持久和可运营。当前 Main UI 仍半双工，IM 没有 100 词硬限制，存储虽可外置但没有无状态弹性计算平面。

为什么不是更低？

核心工作闭环已经完整：Main → WorkBrief → Router → Ticket → Assignment → Worker → verified report → Main → Delivery。并且未知外部结果、停止和 Host 替换都有显式恢复语义。

Router 仍有 Bash / read“不执行”是提示词约定，不是工具限制。所有 Session 先清空默认工具，再按角色显式登记；Main / Router 不拿文件与 Shell。
Worker 直接对外说话Executor 可确认请求、开 PR、回评审。Worker 只 report_ready / ask_human；Main 写结果，Router 的 Delivery 统一出口。
Ticket 是持久业务单位订阅挂 Ticket，不挂 Session，重启更稳。继续保留，并扩展为 WorkBrief / WorkItem / Ticket / Assignment / Session 的完整代次链。
单 SQLite，单机没有存算分离、无端侧 daemon。部分反超：SQLite / PostgreSQL 双后端，本地 / 远端 Environment，但仍是单 Host / 单 Router。
Watchdog 只看退出码基础设施监控，不判断任务进展。拆成外部 Watchdog + Host 内语义 Supervisor；后者提案、前者恢复进程，都不越过人工批准。
飞书 + GitHub两个来源，单仓库。UI / 飞书 / GitHub / 8 类配对 IM / Schedule；邮箱目前仍是手动收件箱，不是 Source。
05 / Evolution
关键演化

From prototype to a governed product runtime旧报告写对中段，
当前代码补上了两端。

Claude 报告判断旧原型“实现了文章架构的中段，没有实现两端”。当前最实质的进步，正好发生在这两端： 前端补了独立的 Main 与产品工作视图，后端补了持久副作用、Host 权限、远端设备、语义监督和可恢复交付。

01 / WORKER

提交验证证据

report_ready 只接受当前 Assignment 的 ready report；普通文本或 idle 不算完成。

02 / MAIN

生成用户语言

Main 读取有界 WorkOutcome 和证据引用，写当前工作对应的可见回复，不接触 Worker 全文。

03 / ROUTER

核准并交付

deliver_result 重新核对当前 report、方向版本与 Assignment 代次，再写入 Delivery。

04 / OUTBOX

真实回执

本地 / 飞书 / GitHub / IM 按 destination 发送，pending 不等于 sent，unknown 必须对账。

DELTA 01 Human continuity

Main 变成独立的第一层

避免 Router 的调度细节占满用户上下文；Main 持有工作索引、结果、问题与按需证据读取。

旧原型→Main / Router / Worker
DELTA 02 Work contract

WorkBrief 成为委托边界

Main 委托一项有目标、约束、验收条件与执行目标的工作；Router 将其拆为 1–4 个独立项。

单 Trigger→Brief / Item / Ticket
DELTA 03 Hard tool scoping

角色权限落成工具白名单

Main 没有文件、Shell；Router 只有计划与投递工具；Worker 才会看到绑定环境的执行工具。

提示词约束→代码强制 allowlist
DELTA 04 Generation fencing

Ticket 与 Session 彻底解耦

一个 Ticket 可以有多个 Assignment 代次。旧代的 job / subagent / report 回调只能审计。

Session 即工作→Ticket 是业务单位
DELTA 05 Durable effects

副作用的“未知”成为一等状态

先保存意图再执行；超时或崩溃不自动重发，按原身份 reconcile。结果状态进入 Delivery 账本。

直接调用→Effect / Receipt / Outbox
DELTA 06 Host authority

重启是 epoch，不是同名进程

Host lease 过期、takeover pending、逐票对账、旧 Assignment 结束，然后才有 successor。

文件锁→租约 / epoch / fence
DELTA 07 BYOM execution

远端是真实的执行世界

设备只持有自己的目录、权限和作业；Host 用加密协议调用，选择远端后不会静默回退本地。

同机执行者→Local / Remote worlds
DELTA 08 Two control loops

Watchdog 与 Supervisor 分工

外部进程处理“服务死了”；语义 Session 处理“工作是不是停滞/偏离”，并且只能提案。

退出码检查→恢复 + 监督

这不是“多了一层”而已

Main 让工作细节不污染日常对话；Ticket/Assignment 让 Session 可以丢失与替换；Outbox 让“谁说话”与“谁执行”分离。三者一起才构成可靠的产品形态。

代价也要说清

Main 忙时仍阻止新输入；结果交付要等 Main 写出用户可见回复；单 Host 所有权提供一致性，也限制了水平扩展。这些不是隐藏缺陷，而是当前取舍。

写权不是进程存活

旧 Host 即使还活着，也因 lease token / epoch 不匹配失去写权；新 Host 必须先写 takeover pending。

先把未知变可见

外部 Effect、远端 job、人工停止和当前问题逐票核对；无法证明的结果保持 unknown 或等待人类。

旧代次不能复活

所有迟到回调带 Assignment ID 与 generation。只有新代次可以唤醒 Worker，旧事实只审计。

为什么是单写者

它牺牲水平扩展，换取无冲突的业务事实。多实例与多写者需要新的分区 / 队列设计，不是再起一个进程。

08 / Bottom line
最后判断

它不是缩小版文章，
也还不是完成版云服务。

它把文章里最容易“只停留在提示词”的部分做成了状态机，把旧原型最容易丢的外部结果做成了可对账事实。 但如果目标是“始终在线、真实多渠道、开箱即用”，现在仍处在产品骨架完成、运营闭环未完成的阶段。

01架构上，三层职责与硬工具边界已经胜过旧原型。

02可靠性上，Host / Assignment / Effect / Delivery 四条代次链是最大护城河。

03产品上，Main / Work / Activity / Settings 已经成形，但全双工与渠道对称性未闭环。

04运营上，BYOM、托管存储和 Watchdog 都有代码，却还没有变成普通用户可依赖的服务。
