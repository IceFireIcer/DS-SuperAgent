## 2026-11-18 包形态最终收口

R5-34 的后续复核发现仓库虽然已删除旧 team runtime，但仍保留一个独立的 `ds-bot` DSH 包；这与“只有一个
DSH 包、现有 UI 原位收口”的验收仍有差距。本次将该目录整体迁入 `superagent/dsh/`，并从应用依赖、profile
bundle、CI、Docker、构建产物和发布入口中删除旧包：

- `superagent` 包根现在是唯一 Host 插件，加载 `src/profile.ts`、`createProductHost`、
  `src/product-http.ts` 和 production Engine；`enginePlugin` 只保留给 CLI、mock 和直接 Cordis 使用者。
- 包 `exports["./client"]` 指向生成的 `dsh/client.js`，`exports["./web-search"]` 指向
  `dsh/web-search.js`；`dsh.client.platform: web` 和 `dsh.bundle.patch` 在同一个 manifest 中声明。
- `cordis.patch.yml` 只插入 bare `ds-superagent`、`ds-superagent/web-search` 和 PostgreSQL/Session rows。
  App 的 bundle 列表只剩 DSH base、DSH Web、voice input 和 `ds-superagent`；旧 `ds-bot` 被加入启动时的
  retired bundle 清理列表。
- 现有浏览器模块 id、i18n namespace 和 style owner 改为 `ds-superagent`。Electron preload/IPC 的产品通道
  改为 `ds-superagent:*`，浏览器 bridge 改为 `window.dsSuperagentApp`；Office 和 web-search 保留原能力。
- `superagent/scripts/build.mjs` 每次先清理 ignored `dist/`。清理前打包目录积累 2,545 个历史构建文件；
  收口后 tarball 为 162 files、约 0.85 MB compressed / 3.94 MB unpacked，并包含 client、Office 和 web-search。
- App、Docker、release workflow、lockfile、UI boundary、change scope、扫描器和文档均改为单包路径。
  Docker 只构建并安装一个 `ds-superagent` tarball。
- Package root 不再等待 Web `connection`；`superagentProduct` 先启动，`/api/product` bridge 独立等待
  `connection` 与 `superagentProduct` 同时可用。无 Web 的 profile 进程和 App 的 Web profile 都能完成装配。
- Docker template 在 `dsh plugin add` 前只允许三个已核验的原生构建 identity
  （`dsh-subprocess-local`、`koffi`、`node-pty`）。pnpm 11 不再以 ignored-build 错误终止安装。

## 入口收口

`superagent/src/index.ts` 现在发布单包根插件；它从 `profile.ts` 取得 DSH profile apply，并从
`product-http.ts` 挂载 `/api/product` 与原生 Session 拒绝。仓库已没有顶层 `ds-bot/`，也没有第二个 plugin
manifest、patch 或 package dependency。

客户端入口只应用 `applyProduct`。产品依赖图现在只剩 Main 对话、工作卡、产品设置和它们实际使用的共享组件；
旧 sidebar、群设置、成员状态、上下文菜单、旧视图、语音房间、旧记忆面板、模型菜单、学习卡和 widget/cell
实现均无消费者并已删除。迁移后发现的旧 message-layout pref 测试及其无消费者 helper 也删除；
`dsh/client.js` 由 `dsh/scripts/build-client.mjs` 重新生成。

应用只启动一个 `ds-superagent` profile，固定 profile 数据目录为 `<data>/superagent`。旧 profile 选择器、
`DS_BOT_PROFILE`、`DS_BOT_CHECK`、第一次启动的旧团队导入、旧 Session 检查、旧 profile Host 和回切分支均已
删除。已有旧 profile、旧业务文件和旧 Session 不会被删除或自动迁移。

独立、未接线且未打包的 `app/ui/`、`app/engine/` 和 Vite renderer 已删除。应用继续加载 DSH 现有 Web
前端和迁入 `ds-superagent/dsh/` 的现有客户端，不新增 renderer 或独立 UI 包。

仓库根部的旧 `browser-plugins/` 包仍引用已删除的 `ds-bot/src/host/browser/*`，已整体删除；保留的 Browser
能力由 R5 `BrowserResources`、Host browser adapter、App BotViews/import IPC 和现有 Browser settings 消费。
Docker 安装 DSH `0.2.1-rc.4` 的单一 web profile，只安装 `ds-superagent`，并把
`DS_SUPERAGENT_WORKSPACE=/workspace` 交给产品。旧持久 profile 缺少 `ds-superagent` 时启动明确失败并要求
换/归档数据，不会继续运行旧团队或自动导入。

## 新入口与边界

产品 Host 只发布：

- `superagentProduct` 公开查询/命令；
- `POST /api/product`；
- 受控浏览器、Office、凭据和导入所需的应用 IPC。

直接 `/api/session/list` 返回空投影，其他 `/api/session/*` 和 `/api/session.export` 被拒绝。原生
Session controller/reference resolver 从产品 Gateway 隔离；Main、Router、Worker 的写入只走 Engine 的公开
DSH loop、Assignment 和 Input 契约。`/api/bot`、旧 SSE/feed、question、delivery 和 resume 兼容 façade 不再
挂载。

`MainWorkCardBrief.capabilities` 保持公开的 `CapabilityId[]`，与 work brief、执行候选和 Worker 观察使用同一
类型。Worker 只读事实现在包含 target、required capabilities、selection source/status/reason、每个候选的
eligible/blocked 与阻塞原因。产品定向测试实际断言了 eligible remote 和 blocked local 两类事实。

## API 外 hooks/tools

- 旧 `list_bots`、`message_bot`、`stop_bot`、`create_bot`、`update_bot`、group 和 capability 管理工具不再注册。
  Main 用 `delegate_work` 形成持久 work brief；Worker 的合法子代理、stop、question、View、memory、MCP、browser、
  Office 和附件由当前 Engine/Assignment world 提供。
- 旧 group relay、`read_own_chat` 和 `read_group_chat` 已删除。新产品使用 Main history、evidence、observe 和
  受权 side query，不暴露旧私聊/群档案。
- 旧 turns/parts/resume/feed/usage/memory/learning hooks 不再启动。业务事实由 Engine 持久化，原生 Session
  只由 `NativeSessions` 和 Session persistence 公开服务运行。
- DSH search、compaction、tools、attachments、workspace 和 Session APIs 继续直接使用公共接口；没有 patch DSH。
- Office、附件、图像、结构化 View、浏览器 App bridge、scheduler、remote device、PostgreSQL、Watchdog 和
  Supervisor 模块保留，并由 R5 产品命令或现有设置页消费。
- 可选 browser、credential 和 memory 导入只看用户明确选择的数据或独立导出，不使用旧团队 runtime、旧 profile
  或旧 Session 自动发现作为前提。

## 数据与失败边界

删除只针对无当前消费者的代码和入口。用户旧 DSH、旧 DS Bot profile、业务库、Session、凭据、workspace 和
attachment 文件没有删除、移动或重写。应用首次启动仍校验数据/工作区和用户 DSH 隔离，并保留卸载/数据移动
的既有保护。

产品 profile 在缺少 `superagentProduct`、`workspaceRegistry`、模型 route、数据库或执行能力时 fail closed；
不会回退旧 core，也不把等待中的工作显示为成功。R5-33 的 Host fencing、Assignment generation、Session writer
epoch、远端 stop 对账、pending pairing/revoke replay 和 credential cleanup 路径未因删除旧入口改变。

App 认真采用首启/Settings 选择的 workspace，并通过 `DS_BOT_WORKSPACE` 传给 Host；Host 同时接受新的
`DS_SUPERAGENT_WORKSPACE`，使 Docker 使用单包环境名。产品 Home 仍固定为 `<data>/superagent`。App 同时把
用户原 DSH home 作为 `DS_BOT_USER_DSH_HOME` 传给 Host，产品目录注册和 workspace 选择会拒绝该目录及其子目录。
没有把 `~/.dsh` 当作产品数据目录。
