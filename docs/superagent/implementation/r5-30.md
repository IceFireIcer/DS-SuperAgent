## 本轮接通

主对话工作卡遇到 `pendingDeviceConfirmation` 时，提供“Check device stop”按钮。按钮通过 `work-reconcile-stop` 把当前 `workItemId` 和 `ticketId` 交给产品 Host；Engine 先重新核对 Main Instance、已接受工作项及其 Ticket 归属，再复用 `reconcileStop`，按原设备作业身份检查并尝试取消。只读客户端无权调用，受权远程客户端沿已有 command 能力与回执协议访问。没有确认原范围静止之前，卡片继续显示 stopping，resume 仍拒绝。

既有核心已持久记录 stop、设备身份、作业状态与未知结果；远端不通时保持 `pendingDeviceConfirmation`，回连后依赖原作业身份与设备报告确认静止。按钮不自动重新执行写操作或迁移 Assignment。

## 2026-11-17 代码验收收口

产品 UI 复核发现 Host 重启后的离线 stop 会被恢复成 `stop.state=stopped`，但 `pendingDeviceConfirmation=true`；原条件先检查 state，工作卡因此错误显示“Stopped · cancellation confirmation is unavailable”。现有 `product-remote-wait` 定向测试先改为该真实持久形态，确认红灯后把 pending-device-confirmation 放在状态显示首位。现在无论引擎进程仍显示 `stopping`，还是替换 Host 已恢复为 `stopped`，只要设备确认未完成都显示“Stopping · waiting for device cancellation confirmation”，并提供原工作卡对账按钮。

新增产品 Host 替换的定向闭环：实际 RemoteDevice + 可断开 HTTP 代理、产品配对、Main 委派 remote-only 后台命令、断连后从 `work-stop` 持久 stop、关闭并重新创建产品 Host、离线时 `work-reconcile-stop` 保持 pending、恢复连接后按原 work item/Ticket/job ID 确认原 managed range cancelled，随后显式 `work-resume` 创建新 Assignment。该证据在同一个 Node 进程内重建产品 Host，不冒充操作系统进程边界；真实第二设备轨迹仍归 T58。重启前后都验证未自动恢复，设备确认前 `work-resume` 返回 `STOPPING`，确认后 `canResume=true` 且 outcome 仍为 stopped。该 pending 期间另有一项显式 local-only 工作进入 `waiting` 人类问题状态，证明 pending/unknown 的远端 Ticket 没有阻塞无关工作。

Spec 复核补出两个身份窗口并已修复：停止对账现在要求当前 Environment 的 device ID 与 incarnation 都和原 Job 记录一致，同一 Environment ID 被重新配对给另一设备时不会向替代设备查询，停止保持 pending；迟到的远端 start 回答在 stop 先持久后返回时保持 unknown/pendingDeviceConfirmation，结果不能清除 stop 或生成 result。

对照四项验收：

1. `work-stop` 在业务事务中立即写停止约束，远端未确认时保持 `stopping/pendingDeviceConfirmation`；产品测试验证没有报告 cancelled。
2. stop、设备、job 与 Ticket 使用原持久身份；现有 daemon restart、Host replacement、错误替代设备、迟到 start 和设备 owner/deadline 测试验证 incarnation/identity，重连不会清 stop 或自动执行。
3. pending/unknown 只保留在受影响 Ticket；同 Host 的独立 local-only 工作继续进入 `waiting` 人类问题状态。连接未恢复时显式 reconcile 仍 pending，不重发写入或换设备。
4. 设备未确认前 resume 被 `STOPPING` 拒绝；确认后只有显式 resume 才可创建新 Assignment，既有 stop/restart 测试覆盖 `CANCELLATION_UNCONFIRMED`、unknown、stopped 与新 Assignment 代次。
