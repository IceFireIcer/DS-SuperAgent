## Standards

首轮阻断为旧 `expectedGeneration` 在命令回执查询前检查，导致成功交接后响应丢失无法按原 command 重放；generation 检查与真正写入也分离，长 probe 期间换代可能让旧回调写入当前工作副本。prepare、verify、request 现在都在核心命令事务内先处理既有回执，再检查并写入 generation；request 还把 generation 带入 Execution 的 requested-record 事务。新增 target probe 延迟测试证明换代后旧请求不会落交接状态。

复核补充指出 verify 仍会重新 probe 后才返回；现改为从 command receipt 或工作副本历史直接返回同一 verified record。最终 switch 授权回调也移到后台范围读取之后，并在同一事务写新代前执行。

第二轮发现 pending remote revoke 只持久化业务状态，恢复后的 Environment 仍可能短暂授权。RemoteEnvironment 现在在撤销开始时立即进入 fail-closed `revoking` 状态；Product Host 在持久化 pending revoke 前调用它，并在启动时先扫描 pending revoke commands，恢复后立即 quarantine 对应 Environment。

UI 复核要求不直接渲染后端异常，且不让 MainWorkCard 承担完整交接领域逻辑。Handoff 状态、owner、nextStep、blocker、targets、copy 与 record 已收敛为 Engine 投影；工作卡抽出独立 panel，已知 blocker 通过固定 code 和 i18n 输出。最终 Standards 复看：**clean，0 个阻断项**。

## Spec

首轮复核确认核心 T39/T40/T41 已覆盖安全边界、flush、作业对账、旧代隔离和中断恢复，但产品入口、历史投影、目标 prepare 核验及 pending revoke 窗口仍不完整。

修复后：

- prepare 即应用 Ticket local/remote/auto、能力、在线、目录、版本、fingerprint、容量和工作副本检查；不合格目标形成 `handoff-blocked`。
- stop、waiting-human、unknown、ready report、paused、无 active Assignment 等状态在投影中明确为 blocked，并显示责任方与 `resolve` 下一步；不会显示可交接动作。
- request 在 requested、flushing、switching 每阶段保留同一记录；Host 重启后继续同一进度与 command，目标离线、停复或授权变化保持 blocked。
- 最终切换事务重新核验源/目标身份和授权；pending revoke 在运行时、Host 重启和交接 switch 中均 fail closed。
- 工作卡支持本地→远端再交回本地；Ticket/Session ID 保持不变，三个 Assignment 代次都可查，只有最新代次 current。

真实第二设备、TLS/SSH、真实模型与生产 PostgreSQL 仍归 T58/发布环境，不因 loopback 产品测试关闭。最终 Spec 复看：**clean，0 个代码验收阻断项**。
