# R5-15：新产品凭据资源管理（增量交付）

- 工单：R5-15 / #107；规格：`docs/superagent/spec-r5.md` D09、D12、D13 与 A21。
- 基线：`dev` 的 `4a6e060`；隔离分支 `feat/107-resource-credentials`。
- 状态：领域、受信 DSH vault、本地 Host 与设置页已接通；本增量接通飞书来源读取和外发的实际凭据消费，Worker 工具与完整验收仍未完成。

## 已实现

`ResourceCredentials(storage, instanceId, vault)` 是仅由受信 Host 构造的领域接缝。创建和轮换只接收先在 vault 中登记的引用；业务库保存 Instance、资源元数据、授权、请求状态和不含密钥的命令回执，不保存密钥值。资源没有默认 grant。授权单独指定 Main/Router/Worker、可选精确 workItemId/Environment/sourceInstanceId 和用途 `source`、`tool`、`outbound`；来源接收和外发必须指定来源 Instance。缺失、失权、跨 Instance、已删除均明确拒绝，无其他来源或全局凭据回退。

受信调用方可以用 `create`、`update`、`request`、`cancel`、`grant`、`revoke`、`delete`；所有写命令有稳定 commandId 和持久回执，相同命令同输入去重、异文冲突。更新/授权/撤销/删除使用 revision 条件。`get`、`list`、`getRequest` 只返回不含 vault 引用的视图。`use` 在每次调用时检查当前 grant，再委托受信 vault 和消费函数使用秘密；vault/消费函数异常只转为固定错误码，不透传异常文本。删除先持久封禁资源，业务记录暂留仅供受信 Host 重试清理的 opaque vault 引用；实际清理确认后移除该引用，投影始终不含引用或原文。

SQLite/PostgreSQL 使用同一现有 `Storage` 事务协议和 `RecordKind` 白名单，无新专用表。新增 `resource-credential`、`resource-command`、`resource-request`；按并行 R5-14 的文件所有权约定，仅在同一白名单中登记 `product-attachment`，本票没有实现附件行为。

## 受信接口与集成边界

- Host 需提供持久且按 Instance 隔离的 `CredentialVault.assertReference(instanceId, reference)` 和 `withSecret(instanceId, reference, consume)`，由其负责安全存放、轮换后旧值清理和删除后的物理删除；本票没有连接 DSH credentials 或 OS vault。vault 引用只在受信创建/轮换命令和内部记录出现，不进入模型工具参数、日志、UI 或 manifest。
- Engine 必须在已认证的受信用户设置入口调用写命令；不能把类实例或 `use` 的消费回调交给 Agent。Engine/Host 要把 `source` 绑定来源接收、`tool` 绑定当前工作与 Environment、`outbound` 绑定发件依据，并在实际适配器调用点再次查当前状态；当前没有这些运行路径的接线。
- `use` 对一次已开始的消费不提供可中断撤权；撤销或删除提交后，后续调用会拒绝。Host 若要求对在途外部动作即时撤销，需另加租约/取消与副作用对账，不能声称本接缝已经解决。
- UI 仍需提供现有设置页中的资源创建、授权预览、轮换、取消请求、撤权和删除操作及真实回执；旧资源导入需要显式预览、选择和冲突恢复。本票没有 UI 证据、真实 vault、真实来源/工具/外发或完整 Engine 产品验收。

## 2026-11-16：受信 DSH record vault 适配层（仍为局部交付）

基于本地 `dev` 的 `12732e8`，独立分支 `feat/107-product-vault` 新增 `superagent/src/product-credential-vault.ts`。核对 DSH 0.2.1-rc.4 安装包公开的 `@deepseek-ai/dsh-credentials` 类型：`CredentialRef.resolve/describe/set/unset` 可能使用进程环境和 `.env` 等 ambient 来源；`CredentialKey.readRecord/modifyRecord/deleteRecord` 是插件自有记录路径，没有该回退。现有 `product-host.provider-key` 继续使用前一种 API 和 `settings.describe({ redactSecrets: true })`/`settings.mutate` 管理模型 provider key，不作为新资源的私有 vault。适配层只依赖公开 record 契约的结构子集，不引入 DSH 安装内部路径或新依赖。

`ProductCredentialVault` 只接受受信 Host 持有的 record 服务：`create(instanceId, value)` 写入以产品 profile 插件名为 scope 的 `ds-superagent-profile/vault-<Instance SHA-256>-<随机 UUID>` `api-key` record，返回不含值的引用；`rotate` 在同一 record 的 `modifyRecord` 内校验旧记录并更新值；`revoke` 删除 record 并核实已不存在。`assertReference` 和 `withSecret` 每次重读 record，只接受精确 Instance 对应的键与非空 key，不接受 `env`、别的插件键、缺失或撤权记录，也不调用 ambient `resolve`。创建核验实际读回值；provider/消费方异常不传播其文本、cause 或 secret。业务库依旧只保存引用、grant 和不含值的命令回执。消费回调只能由受信 Host 提供，不能暴露给 Agent。

此模块目前不从共享产品入口导出，未在实际 Host 构造或调用；测试以单独编译模块和内存 record mock 验证公开方法形状，并与现有 `ResourceCredentials` 的隔离 SQLite/grant 使用接缝联测。它不证明真实 DSH profile 的持久化、跨进程锁、provider 错误后的重试或真实密钥行为。vault 写入与业务事务不共享原子提交：Host 接线时须处理创建后业务命令失败的孤立 record、资源删除前后的物理清理与结果未知对账；在途消费的撤权同样没有被取消。Engine 公开命令/查询、已认证 Host/UI 设置入口、来源接收、工具调用、外发调用点和旧资源导入尚未接入，#107 不可关闭。

验证：Node 24.22.1 下 `npm test -- test/product-credential-vault.test.mjs test/resource-credentials.test.mjs` 为 11 通过、1 跳过（既有 Windows PostgreSQL 夹具）、0 失败；`npm run typecheck`、`npm run lint`、`node scripts/check-ui-boundary.mjs --base 12732e8` 通过。另以官方包公开的 `credentialKey` 函数验证产品 scope 与 record id 格式。未跑全量 CI，未读取用户 DSH 数据。

## 后续增量：真实 provider、Host 与设置页

上述“只用内存 mock、未接 Host/UI”的陈述是此前独立分支状态。现已用隔离目录装载 DSH 0.2.1-rc.4 的公开本地 record provider，验证相同命令 ID 的 vault 创建与重启读取。`ProductCredentialManager` 用受信 Host 的 Engine lease 包装存储管理资源，创建、查询、请求、授权、撤权、重命名与删除进入产品 `/api/product`；远端客户端管理请求在服务端拒绝。旧 Host lease 被替换后，写命令在同一事务被拒绝。现有设置页原位提供资源及 grant 管理；新资源不显示原文或 vault 引用，也不自动获得 grant。

创建命令派生稳定 vault key；丢失响应后重试不会另建 record。删除先持久封禁业务授权，vault 删除失败时视图带 `cleanupPending`，同一删除命令、另一次重试或 Host 启动扫描都能继续清理；确认后业务 tombstone 不再保留引用。原 provider API key 设置路径仍独立，不能拿它代替新资源授权。设置页明确显示：当前 grant 是已保存的授权事实，尚无来源、工具或交付消费者。Node 24 隔离 Host/真实 provider 与管理接缝定向测试通过，前端设置交互/翻译/生成定向测试通过；没有使用真实账号或密钥，PostgreSQL fixture 与在途撤权仍未验收。

**未完成且阻止关闭 #107**：真实来源接收、Worker 工具与外发适配器必须在各自调用点按 Instance、role、work/Environment、来源和用途逐次消费 grant；设置页尚无秘密轮换入口，旧资源可选导入与副作用结果未知对账未完成。不能把“授权记录可管理”表述为那些能力已用上新凭据。

## 延迟 vault 写入与 Host 恢复边界

本地增量将创建意图的恢复状态扩为 `pending/created/abandoned`。替换 Host 清理未取得业务回执的 vault record 后保留 `abandoned` 事实；同一旧命令不能重新创建资源，业务创建事务会在写资源前检查意图仍为 `pending`。这样，旧 Host 的异步 vault 写若在首次清理后才落下，下一次 `resumeCreations` 仍可用保留的意图定位并删除它。Node 24 定向测试以两个 Manager 交错覆盖“恢复先完成、旧写随后成功或在写后中断”两种次序及分页续扫；凭据 Manager/Host/领域联合回归 15 通过、Windows PostgreSQL 夹具 1 跳过，typecheck 与 lint 通过。

Host 启动与后续定时轮次重复扫描创建意图，每轮最多扫描 10 页，超过该界限保存游标供下轮继续；显式 `resource-cleanup` 也可触发扫描。两轮扫描之间迟到的旧 Host 写会在后续轮次清理。这仍不是跨进程 exactly-once 证明：真实多进程替换、长期 provider 故障及 PostgreSQL 尚未验收；不能仅凭本地交错测试关闭 #107。

## 2026-11-16：飞书来源与外发消费者

`feat/107-feishu-credential-use` 从 `dev` `509bab6` 独立实施。用户在现有凭据资源设置卡选择某个飞书来源的资源，选择仅持久保存该资源 ID 与受信 Host 根据配置计算的精确来源 Instance；不能由消息、Agent 或远端客户端提供来源 ID、role 或 purpose。该设置操作遵守 Host 租约，允许清除选择。选择后的来源重新连接；没有资源、DSH record 服务、当前 grant 或 vault 原文时，接收保持失败，不尝试平台网络请求。设置页展示需要的 `Main/source` 和 `Router/outbound` 精确来源授权；工具授权仍不可用。

飞书 OpenAPI 每一次实际 HTTP 请求都经 Host 提供的受信回调调用 `ProductCredentialManager.use`：setup、成员/聊天/消息页与后续 poll 使用 `source`，外发前的原生消息归属核验与 reply POST 使用 `outbound`。回调把本产品 Instance、运行时 sourceInstanceId 与固定的 Main/Router 角色绑定到选定资源；读取当前 grant 和 DSH record 后才可在回调内取得应用密钥。令牌缓存仍在进程内，但每次调用先验 grant，选定的密钥值改变时不复用旧 token。密钥不会返回 UI、prompt、投影、manifest 或异常文本。已记录的外发回执只用于已发事实对账，不触发新的网络消费。

显式配置 `DS_SUPERAGENT_FEISHU_APP_SECRET` 仍是原有受信进程环境 legacy 路径，状态标记为 `legacy`，不允许以资源选择命令把它伪装成受管授权；要使用受管资源，须移除该环境密钥并重启 Host。若已持久选定受管资源，再带着 legacy 密钥启动同一来源，Host 明确报 `INVALID_CONFIG` 且不启动飞书网络，不能以环境密钥绕过已撤销的 grant。没有环境密钥但提供其余飞书身份配置时使用 `managed`，必须选择资源并分别授权，绝不回退到环境或另一个 Instance 的资源。来源与外发当前不从 Worker work/Environment 发起，带 workItemId 或 environmentId 限定的 grant 不匹配这些调用；Worker tool 的真实受控使用留待独立增量。

隔离 Node 24 验证使用临时 SQLite、独立 DSH record provider 与 mock Feishu transport：从产品 Host 入口创建/选择资源后 setup 和来源读取实际出网；缺 grant、错误来源、撤权和重启时无后续网络请求，缓存 token 不能绕过逐次授权。Runtime 外发分别在消息归属 GET 和 reply POST 使用 outbound grant，只有 source grant 时两者均拒绝；两次请求之间撤权可阻止 POST，明确的 HTTP 503 仍按原状态归类。显式 legacy 路径拒绝资源选择，持久受管选择与 legacy 密钥冲突时不出网。Node 24 定向后端 30/30、设置页 1/1，通过 typecheck、lint、客户端生成一致性与 UI 边界检查；不读取真实 DSH 数据、不连接真实租户、不跑全量 CI。

本增量不解决已经开始的网络请求的即时取消、平台响应未知的跨进程对账、Worker 工具消费、凭据轮换入口、PostgreSQL 合约和真实租户验收。#107 仍 OPEN。
