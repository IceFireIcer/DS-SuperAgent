## 产品装配

`ProductHostConfig` 现在明确支持两种业务存储装配：现有 SQLite `databasePath`，或共享
`PostgresStorage` 的 `postgres` 配置。PostgreSQL 模式需要受信的本地绝对 `stateRoot`，继续保存
proactive preparation、Environment assets 等 Host 本地文件；不能再从数据库路径推断这些目录。
两个存储字段必须且只能提供一个，SQLite 调用和测试与托管配置继续共存。

托管 profile 从进程环境读取 `DS_SUPERAGENT_POSTGRES`。值是受信的 `PostgresOptions` JSON，凭据只存在
Host 环境，不写入 patch、业务投影、日志或仓库。`superagent/cordis.patch.yml` 在存在该配置时停用基础
JSONL Session provider，并挂载现有 `ds-superagent/session-persistence-postgres`；产品业务事实与原生
Session 仍分别持久，不宣称跨库事务。

同一 profile 还读取 `DS_SUPERAGENT_HOST_ID` 和 `DS_SUPERAGENT_LEASE_MS`，把稳定的 Host 身份和 lease
预算交给现有 HostLease。默认构建、本机 SQLite profile 和既有测试不需要这些环境变量。

## 替换顺序与工作恢复

产品 Host 创建主 Engine 后立即取得当前 Host epoch，然后才创建 ProactiveWork、恢复产品操作并启动
gateway。此前如果旧 Host lease 已过期，Engine 在显式 acquire 之前的守卫事务会返回
`HOST_LEASE_EXPIRED`；现在接管先推进 epoch，后续事务使用新 token。

真实 `ask_human` 会把旧 Assignment 标记为 `ended`。原接管扫描只检查非 ended Assignment，因此会把仍
处于 waiting-human 的真实工作完全跳过。修复后，ended Assignment 只要还有当前 Authority 需要承接，
仍进入同一 `takeOverTicket`：

- waiting-human Attention 或 Ticket constraint；
- 未完成 stop；
- pending Intent；
- running/unknown device job 或 subagent；
- unknown Effect、MCP、browser operation 或 preview cleanup。

普通成功报告后的 ended Assignment 不重新进入接管。开始替换后，新工作仍被 pending takeover 挡住；
stop、waiting-human、unknown 和退权状态不会被清理或自动放行。旧 Host 的 HostLease token、Assignment
generation 和 Session writer epoch 继续由原有 fencing 链路隔离。

## 三层运行与断连重接

托管 Host 继续创建同一 Main、Router 和 Worker 配置。Main 通过持久 WorkBrief、Router Session 和固定
Ticket 委托工作；Worker 提问、停止、报告、inbox/outbox、配置 revision 和结果仍由原 Engine 对象处理。
替换后不创建第二套 Main 或“最近工作”替代身份。

认证客户端继续使用 R5-32 的 `ClientAccess` 和 `createClientGateway`。重连快照读取同一 Main
binding、用户消息、工作卡、Attention 和 Router/Worker 观察；持久事件游标仍按原 Instance 补读。关闭
客户端或 Host 进程不会关闭工作事实，结果也不会因为 UI 重连而被重放成新的命令。

## 分层权威证据

| 权威 | 实现 | 定向证据 |
| --- | --- | --- |
| Instance 事务锁 | 共享 `PostgresStorage` coordinator row | 本票两进程产品运行使用同一 PostgreSQL Instance 完成 lease、业务提交和 Session 日志 |
| Host fencing | 进程 owner token、Host ID、durable epoch | 新测试保存 epoch 1，强杀旧进程，等待 lease 过期，替换后读取 epoch 2 的 completed takeover |
| Assignment 代次 | 原 Ticket/Session 与 current Assignment | waiting-human 接管保留 generation；人工回答后由当前代继续并产出 verified report |
| Session writer | writer lease、durable epoch、旧 handle 拒绝 | `session-persistence.test` 的 failed flush/service flush/epoch moved 4/4；PostgreSQL provider 继续复用 T43 身份契约 |
| 设备作业 | 原 Environment/device/job identity | `host-takeover.test` 的 live remote job adoption 通过；pending stop/unknown blockers 继续由现有执行层处理 |

`host-takeover.test` 的 11 项定向回归同时覆盖合法 resumed 接管、stopped、waiting-human、unknown
job/effect、live remote job、queued input、pending takeover、同 Host ID 新 epoch、撤权和无 native runtime
的 fail-closed 行为。

## 故障与恢复边界

业务提交失败与 Session flush 失败分别记录：Main 在原生回复已完成后拒绝业务投影写入，刷新仍以原消息
身份补回且不重复调用模型；Session provider 在 flush/close 失败时保留 writer ownership，epoch 已经移动
的旧 handle 拒绝 append、flush 和 close。没有把二者包装成跨库原子提交。

本轮曾尝试沿用 `input-recovery` 的跨进程 `flush-failure` 注入，但该 fixture 在 25 秒内没有到达预期注入
边界，因此不计为通过。对应的 Session Provider 失败与写权保留改由更窄的 4 项测试验证；这是个仍应单独
修复或重新设计的旧故障夹具限制，不影响本票成功路径。

## 定向验证

- Node 24.22.1，隔离 PostgreSQL 的真实两进程产品测试 **1/1**：产品 profile、共享 PostgreSQL 业务库和
  Session provider、同 Main/Router/Worker Session、客户端发起工作、等待人类问题、断开客户端、SIGKILL
  旧 Host、30 秒 lease 过期、替换 Host、completed takeover、原 generation/Attention、同一 Main 重连、
  Session 仍可写、人工回答、Worker 写文件与验证命令、ready report、同一 Main 结果。
- `host-takeover`、`profile`、`t59-profile`、`product-client-gateway` 联合定向 **21/21**。
- 新增 PostgreSQL profile 配置与 patch provider 选择断言后，`profile` **7/7**。
- 业务投影提交失败 **1/1**；Session failed flush/service flush/writer epoch **4/4**。
- `npm run typecheck`、`npm run build`、`npm run lint` 和新增 fixture 的 `node --check` 通过。
- 未运行全量 CI；没有真实临时服务器、第二设备、持续四目标报告、真实模型或真实飞书租户证据。

这些环境验收继续归 T58/#92 与 T55/#83。本票只证明同一产品的隔离 mock/PostgreSQL Host 替换闭环和
可部署装配接缝。
