# DS-SuperAgent 独立产品实施计划 R5

- 日期：2026-11-14；状态：Q1—Q14 产品决定已收敛，准备综合正式规格。独立产品不保留旧 Bot 架构或旧 ds-bot 兼容义务。
- 主 Agent 是独立模型与独立上下文，不是 Router 的 UI 投影；现有代码只有 Router/Worker，三层属于明确的新增架构变更。
- 替代本目录 R1 的“长期 Bot/群行为全部等价移植”假设，不修改正式 v2.1 或既有实现记录。
- 范围覆盖已要求的浏览器、MCP、Office、文件、记忆、日程等能力及现有前端组件复用；旧团队治理、Bot 互派、群轮次、旧历史入口和旧版本协议不作为需保留的能力。
- 本轮不实施产品变更，不迁移数据，不停旧 profile，不发布新规格或 tickets。

## 1. 为什么重新排序

R1 从 85 个旧接口出发，把 Bot 私聊、Main Bot、群成员轮次映射成新核心功能，可能得到“多 Bot 团队外加任务账本”，而非原定的连续协作者。原规格 D01/D05/D12 已说明：Router 做工作间协调，Worker 深入具体工作，Thread 与 Ticket 多对多，角色不是固定 Bot 私聊的主人。

当前桥接也不是最终模型：`ds-bot-host.ts` 按 UI Session 创建不同 instanceId/Engine；`ds-bot-adapter.ts` 为一个 scope 固定恢复一个工作绑定。这条窄适配可作历史基线，但不能靠补齐旧接口直接变成“一次讨论中多项工作、跨信道继续同一工作”的产品核心。同一原生事件普通重复接受仍复用回执，一条 A+B 请求拆成两项新工作也不是当前已支持契约，必须补规格与实现，不能只改装配。详见 [协作模型复核](collaboration-model.md)。

## 2. 保留什么，重建什么

- **保留能力**：浏览器、凭据、MCP、Office、文件、模型配置、记忆/搜索、日程、问题卡、历史和可恢复执行等都要有明确归属和场景证据。
- **复用界面**：复用现有聊天、气泡、卡片、侧栏、设置与视觉组件；不另造替代前端。侧栏项目、成员标签、停止按钮等的含义若变化，必须先做语义映射和维护者确认，不能假称“UI 完全不变”。
- **重建协作**：主 Agent 负责用户交互与委托，Router 负责工作分解与协调，Worker 在隔离上下文执行；角色预设用于能力配置，不复活长期 Bot 互派。
- **保留保护**：隐私范围、凭据隔离、工作授权、人工 stop、未知结果核查与新产品工作历史继续有效；不增加旧 Bot 档案或兼容入口。
- **重建界面语义**：主对话默认可交互；Router 与 Worker 只读观察；Worker 自动出现、不抢焦点，结束后保留新工作历史。旧联系人、团队/群管理和旧历史入口从新 UI 移除。

### 不变量

1. 同一授权工作空间维持一条连续主对话及逻辑 Main，切换观察页面不创建新 Main；不同私人/团队隐私范围隔离。Router 与有效活动 Host 在其 Instance 内保持唯一权威；上下文换代不切断主对话身份与连续性。
2. Ticket 是工作；Assignment 是执行安排；Session 是上下文；Thread 是讨论来源。Thread 与 Ticket 多对多，同一讨论允许并行独立工作。
3. 来源事件先持久化和核查 scope。外部新的人类请求进入所属 Main 后委托 Router；已关联工作跟进与环境事件受控直通。已有 owner 未交回时 Router 不重复接单，普通步骤不逐条唤醒 Main。
4. Worker 读取原始证据，只能在 Mandate 内执行；范围外 handback。跨任务事实经受控协调，不用任意 Bot 对聊绕过授权。
5. 主要结果与人工问题受统一交付规则及 Outbox 管理；Worker 的受控确认/回答窄入口不等于每个 Worker 随意向用户发消息。执行 transcript 仅按需且经权限展示。
6. DSH 保持原生 loop/Session/模型/工具运行时，Domain Engine 仍为唯一领域写入口。纯设置、诊断不必生成 Ticket。
7. 不保留旧 Bot 团队运行模型、旧协作历史入口或旧协议兼容；旧配置和资源仅作可选、经预览确认的提取/导入，不继承 Main Bot 高权限，不重放旧派活，不删除或写入用户自己的 DSH 数据。
8. Main、Router、Worker 各有独立 model route、Session 与上下文。Main 默认接收有界回执和关键状态/结果/问题；可查询状态、按需读取获授权的有界交付物/证据，不接收完整 Worker transcript 或逐条执行输出。
9. Main 通过 WorkBrief/FollowUp/Control 驱动 Router，不直接创建 Ticket/Worker 或进行文件修改、Shell、浏览器操作。明确目标的 UI 停止直接交受信核心，不等待模型；Router/Worker 观察区保持只读，不能从日志发起 prompt、steer、审批或工具重放。
10. 有效问题卡的明确答案可由主对话 UI 直接交核心，校验工作、问题版本和用户权限后推进原工作；Main/Router 只需接收事实通知，不重复改写。Main 模型故障不阻断已授权工作、核心事实查看、明确停止或有效问题卡答复；新自然语言输入排队，恢复后按原身份补读。
11. Worker 条目自动出现、不抢焦点，结束后保留历史；角色模型/指令在既有设置页独立配置，只对后续合法请求生效，不重跑任务。结果默认回原信道，私人上下文不自动带入公开 Issue 或群聊。
12. 输入框“停止生成”仅停止 Main 当前回复；已提交/已派出的后台工作继续。工作卡停止和全部停止分别显示明确范围，提交结果未知时按原委托身份对账。

## 3. 目标职责，而非旧对象逐一改名

| 组件 | 新模型中的职责 | 对旧产品的处理 |
|---|---|---|
| 现有 UI 组件与产品投影 | 主 Agent 默认对话、工作摘要与问题；Router/Worker 详情按只读观察视图展开 | 复用组件，移除 Bot 联系人、内部群管理和旧历史入口；UI Session 不等于一个工作 |
| Product boundary | 新产品的受信身份、Instance/Thread 作用域、消息身份、命令与查询 | 可演进既有接缝，但不对旧客户端、旧 roster/成员对象或旧 API 行为作兼容承诺 |
| Instance Engine | 持久输入、研判决定、订阅、授权、Ticket/Assignment、恢复与效果账本 | 每个共享范围一个核心；旧私聊 scope factory 不作为最终拓扑 |
| Router | 处理 Main 委托、候选、工作分解/关联、跨任务事实和有界回传 | 不等于 Main Bot，不直接对用户聊天，不替 Worker 规划任务内实现步骤 |
| Worker 与内部子代理 | 工作级调查、执行、验证、报告、范围内跟进；内部可有 Agent Team | 不等于固定具名 Bot；角色预设可复用，Session 可复用或显式换代 |
| Capability/Context adapters | 浏览器、MCP、Office、目录、凭据、授权记忆和原文读取 | 迁入能力与资源，不迁入第二套 Bot 调度器；资源作用域必须显式重新映射 |
| Sources/Channels/Operations | 来源 scope、事件与游标、统一交付；日程、监督、Watchdog 与健康管理 | 外部群消息是来源 Thread，不等于原产品内部 Bot 群轮流发言 |
| Persistence/Optional import | 新产品业务事实与 Session 日志分域；可选预设/资源导入、初始化和自身备份恢复 | 不加载旧工作状态或旧聊天档案，不恢复旧身份/权限，不建设旧核心回切通道 |

## 4. 用场景验证协作，再适配接口

### 最早必须跑通的竖切

1. 用户在同一主对话说“修复 A，并独立调查 B”：主 Agent 形成一份 WorkBrief；Router 将其拆为两项工作，由两个隔离 Worker 并行处理，而非绑定一个 UI Session 的单 Ticket；两项工作自动出现在只读执行列表。主 Agent 只收到两项工作的有界摘要，不收到 Worker transcript。
2. 用户在该讨论补充“A 先不要发布”：有依据地进入 A 的原 Ticket/当前执行，不另建第三项工作，也不改变 B；歧义时提问而不是按最近窗口猜。
3. GitHub PR/评论关联 A：在同 Instance、权限和证据核验后关联 Thread；后续事件直通 A，context-only 不扩权。
4. A 遇到范围外的新要求：handback 后才重新研判，不把任意主题都塞进原会话；多 owner 时遵守全部交回约束。
5. A 等待用户/被停止/结果未知时，B 可继续；重启不解除 stop，未知外部结果先对账。
6. 用户得到统一的确认、问题和结果；原 Worker 工具轨迹仍可查，但不会混成多个 Bot 的无节制对外发言。点开 Router/Worker 只读视图不会夺走主对话焦点，也不提供绕过主入口的写操作。

### 必须先补齐：复合请求分解契约

首项竖切不只是让两个不同消息产生两个 Ticket，而是支持用户一条明确请求中的独立 A/B 工作。当前核心的接受去重、评估 item、attach 和 manual requeue 都不能直接作为此契约已经存在的证明；实现前须在 to-spec 中明确：

- 保留一份不可变原生来源事件，不伪造两条用户消息；工作项分别有持久稳定身份和独立 Ticket，记录它们来自同一次分解决定。
- 每项工作保留自己的 scope/Mandate、原始请求依据、约束和交付条件；Router 的拆解不增加用户没有提出的要求，也不把 A 的发布权借给 B。
- 分解结果及接受关系可按原请求查询；网络重试、模型重复建议和重启不能再次创建同一批 A/B 工作。稳定身份如何形成与修订由新规格明确，不能临时按模型重写后的文本猜。
- 分项创建可能部分提交时，记录哪些已提交、哪些未创建；重试只能承接原决定并补齐缺项，目标变化应显式冲突/重新决定，不重复派发已存在工作。
- 明确原事件与各 Ticket 的订阅/ownership、后续指代、handback、停止/回答目标及统一交付关系。关联、输入投递和工作接受是不同事实。
- 可先用“两条独立消息”验证已有并发基础，但它不能替代“一条复合请求”的最终验收。不能复用人工 requeue 把整段 A+B 再做一遍来伪装分项。

同 Thread 多 owner 的 fanout 不是自动语义分流。以上第 2 项还要检查其他工作收到输入时不越界承接、必要时 handback，并区分“输入已持久投递”和“执行者已确认采用方向”。停止/回答等控制动作要带可核查目标，不能因为复用原 Bot 按钮就按联系人猜要停哪项工作。

这些是原 Super-agent 意图的验收场景，不代表当前桌面桥已支持。先用隔离 mock DSH/来源 fixtures 建证据，后续按授权补真实模型、信道、设备与原生平台。

### 接口盘点方式

85 个旧 HTTP 操作、模型工具、hooks 与客户端继续用作处置清单，每项标为“保留能力按新协议接入 / 三层语义重构 / 删除旧机制 / 可选配置资源提取”。旧兼容和旧档案入口已由 Q13 排除；不以逐操作兼容为完成标准。保留能力仍需授权、数据归属、错误/恢复、UI 回显与验收；九个功能族清单不等于 85 份已实现的新合同。

## 5. 候选实施顺序

阶段 0 综合已经回答的 Q1—Q14，显式替代旧规格冲突约束，不再征求相同方向。其后做窄而完整的竖切，各阶段仍需拆成单上下文可完成的票；只有文件归属不交叉且依赖已完成的工作才并行。

| 阶段 | 目的与主要内容 | 通过门槛 |
|---|---|---|
| 0. 三层角色、既有决定与功能处置基线 | 明确 Main/Router/Worker 的模型、Session、上下文、工具、输入所有权；主 Agent 默认可交互、Router/Worker 只读、Worker 自动发现；逐项标记旧 Bot/群/工具与资源处置 | Main 独立于 Router 的职责和协议无歧义；Main 默认上下文不含 Worker executor 事实；85 操作及 API 外能力无遗漏；不把线框当产品实现 |
| 1. MainSession、WorkBrief 与共享协调核心 | 一 Instance 一个逻辑 Main + Router + Engine；主 Session 持久化、WorkBrief 稳定 ID、Router 回执、Main 上下文投影与恢复；复合请求分项身份/Mandate/幂等；移除“一个私聊=一个 Engine/工作” | 重试同一 WorkBrief 不重复建工作；Main 与 Router 可独立恢复；同 Thread 多 Ticket 与单事件分项分别验证；不同 Instance 隔离有证据 |
| 2. 真实主对话到并行工作的竖切 | 复用 composer/聊天组件接用户事件、Main->Router WorkBrief、Router 分项、Worker 并发、Router->Main 有界回传、Attention；只读 Router/Worker 观察视图 | 同一条 A+B 请求形成两项独立工作并行；Worker 自动出现而主对话不丢焦点；Main 收不到原始 Worker 日志；只读视图无写入口且服务端拒绝写请求 |
| 3. 三层跟进与可恢复协作 | Main 的 FollowUp/Control/AttentionAnswer 到 Router，Router 的订阅 fan-out、handback、跨任务事实、方向变化、Ticket stop/resume/unknown；只把有界更新回 Main | 跟进不重复建任务；用户在主对话回答；停止 A 不停 B；Main 断开不影响 Worker；重启不解 stop，旧代回调无效，未知结果不盲重做 |
| 4. 三层配置、资源授权与 UI 完整性 | 独立模型/指令、只读视图、问题/停止快路径、故障事实卡、新工作历史、预设与资源授权；移除旧团队/群 UI 依赖 | 配置不影响在途回合；观察无写旁路；停止回复不取消工作；新历史可查且无旧档案入口 |
| 5. 旧产品执行能力接入 | 浏览器/接管、MCP、密钥、Office、附件/图像/Views、目录、子代理/jobs/PTY、模型设置逐项接 port；核对旧团队工具对原生 subagent/workflow 的屏蔽 | 能力可经新工作执行、取消、对账与回显；凭据不进入 prompt/log；旧工具策略不剥夺合法 Worker 内部委派，旧 team tools 不作为第二 dispatcher 装回 |
| 6. 记忆、事件与常驻能力 | 授权记忆/学习/搜索/side query、日程 Source、GitHub/飞书、主动规则、监督/Watchdog、远程/托管及运维 | 原能力和四目标分别有场景证据；角色预设不共享私人记忆；来源事件不固定投给旧 Bot Session；独立部署与设备边界正确 |
| 7. 新产品初始化与可选导入 | 独立配置/数据目录；可审阅角色预设、资源清单与显式归属映射；凭据保持受控引用，不导入旧工作/Session 全量状态 | 虚构资料验证选择/取消/重复导入和授权；不混合私人资料、不恢复旧身份、不修改原件 |
| 8. 移除旧架构与兼容代码 | 清理旧 Bot roster/互派/群 round/Main Bot 权限及对应 UI；去掉旧档案、旧 profile 选择/回切和兼容 façade；统一产品身份 | 构建与运行仅新核心消费输入；保留能力无误删；无旧兼容入口和自动加载旧数据；客户端生成一致 |
| 9. 独立产品完整验收与发布 | 三层四目标、能力/权限、真实原生客户端、来源/远端/常驻；新产品自身备份、升级和恢复 | 领域/mock/真实环境证据分层；新历史、授权和恢复通过；不以完整旧迁移或回切作为发布前置 |

### 不能跨越的门

- Q1—Q14 已确认，正式实施前综合为规格并替代冲突要求；不因原规格还写着旧团队 UI 就恢复已排除的架构。
- 阶段 1–3 未证明原 Super-agent 协作，不先铺完 85 个 route 然后宣布换芯。
- 能力尚缺时，不能把“重构协作”当作放弃浏览器、记忆、日程等功能的理由。
- 旧架构与兼容入口按 Q13 移除；保留能力的缺口和新协议拒绝如实说明，不能把删除旧 API 冒充能力接入完成。
- 不自动加载或执行旧派活；数据保护、来源唯一消费、新产品自身升级/恢复仍需验证，但不维持旧 profile 共存或回切。

## 6. 可选配置/资源导入与数据保护

- 默认独立初始化，不保留旧 Bot/群 ID 的兼容语义、旧 Session 档案浏览或完整旧数据库加载。
- 旧名字、指令、模型、头像、技能可审阅后提取为新角色预设，不创建旧 Bot，不继承 Main Bot 管理权。
- 记忆、浏览器登录态、credential grants 与工作目录分别预览归属；明确选择后绑定新角色/工作空间/Environment，不自动全局合并。
- 不导入旧 in-flight/stopped/unknown 为执行队列；新工作需要当前授权和新身份，旧委托不自动重放。
- T50–T53 等已有旧 archive/切换模块不作为独立产品交付前置；引用按新用途审查，最终无用路径清理，不为保留模块恢复旧兼容。
- Secret 仅经受控 vault/reference 使用，不进 prompt、manifest 或日志；开发只用虚构 home，不读写用户自己的 DSH 数据，不以架构移除为由清空磁盘原件。

## 7. 独立品牌、协议与发布

公开品牌为 DS-SuperAgent，使用自己的配置、数据和启动入口。显示名、app 标识与数据位置按独立产品规格落实；不要求旧安装升级兼容、旧 profile 选择器、API alias 或旧核心回切。单运行入口不意味着合并不同隐私范围。

新协议按 Main/Router/Worker 与受控查询/命令设计，可复用既有实现的有用形状和公开 DSH 接缝，但不建设面向旧客户端的 `/api/bot` 兼容 façade，不伪造 roster/成员/群轮次。客户端与服务端共同演进，仍在现有前端内改动，不创建替代 renderer。

## 8. 完成标准分成三组

1. **协作正确性**：连续、高效、主动、持久按实际场景验证；同讨论多工作、跨 Thread 连续、fast path、统一交付、stop/recovery 与授权成立。
2. **能力与保护完整性**：85 个旧操作和 API 外能力全部有处置，保留能力正常/拒权/重复/中断/历史/回显场景通过；语义重构项通过维护者确认的新验收，不用旧群轮次测试冒充新协作验收。
3. **产品交付**：既有 UI 组件复用且语义清楚、原生客户端/适用平台、mock/真实环境证据分层、品牌/升级/迁移/回退和唯一 profile 通过。当前模块存在或单测通过不证明全产品完成。

## 10. 风险与停止条件

| 风险 | 处理与停止条件 |
|---|---|
| 把保留 UI 当成保留 Bot 派活模型 | 分开视觉组件、交互语义与领域规则；每个旧控制项标明新含义；未确认不实施 |
| 一次聊天永久绑定一个 Ticket，独立请求被吞进旧工作 | 阶段 1–3 先验证多工作/订阅/handback；歧义明确提问，不固定按最新 Session 路由 |
| 用 Thread 多订阅冒充一条复合请求可建多个新工作 | 单事件接受去重、batch item 与 attach 的能力边界先核实；分项 scope/授权、稳定身份和部分提交重试须先规格化；不复制原事件或滥用 requeue |
| Main Bot 权限或私人资源被预设偷偷继承 | 授权与配置分离；只提取经审阅配置，不导入旧身份；资源与授权负对照验收 |
| 新 Router 被做成重型 Team Lead 或中央消息转发瓶颈 | Router 不拆单任务内部步骤；已有 owner 输入直通；内部 Team 只属 Worker 工作范围 |
| 用全量迁入为理由恢复第二套旧 dispatcher | 来源/任务/Outbox 只由新核心拥有；team tools、群轮次和 resume hooks 单独处置 |
| 用语义重构掩盖功能减少或任意重做 UI | 全量能力账本无遗漏，变更须确认；只复用/必要接线现有 UI，不建替代 frontend |
| 借可选导入恢复旧 Bot 或兼容层 | 导入仅初始化新配置/资源，不加载旧 Session/工作队列，不恢复管理员或旧 dispatcher |
| 以静态图或少数测试宣称实现已完成 | 本稿标事实/候选/待确认；实现和验收由后续规格及实际证据证明 |
