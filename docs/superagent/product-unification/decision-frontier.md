# 三层方案的设计访谈记录

- 开始日期：2026-11-14。
- 当前阶段：Q1—Q14 已全部收敛；Q13 按维护者修正为移除旧 Bot 架构、不保留旧历史入口、不做旧 ds-bot 兼容。准备将决定综合为正式规格。
- 记录规则：用户已经表达的要求、源码事实、代理建议分别记录；不把建议当作回答。协议字段、票据编号、实施顺序在产品边界收敛后细化。

## 已确认的前提

1. Main 是独立 Agent，有自己的模型配置与会话上下文；它向 Router 委托工作。
2. Router 分解工作并交给隔离的 Worker Session 执行。
3. 目标是保持 Main 的上下文清晰，不把 Worker 的执行细节全部灌回主对话。
4. 主 Agent 默认显示且可交互；Router 和 Worker 的过程可查看，但不作为可聊天的执行入口。
5. Worker Session 出现后应在 UI 自动可见。
6. 在现有前端内复用组件，移除旧 Bot 协作架构；DS-SuperAgent 按独立产品演进，不保留旧协作历史入口或旧 ds-bot 兼容义务。
7. 沿用用户先前的文件分工约束：并行代理不同时读写同一文件。可证明文件范围不交叉的独立工作才并行，有依赖或可能共享文件时串行/交接；这不是本轮新增待批准问题。

以上角色分离的依据见 [ADR 0001](../../adr/0001-separate-main-agent-from-router.md)。模型配置独立不代表必须购买或选择三个不同的模型。

## 已有源码事实

先前源码核查显示，当前 NativeSessions 与角色配置仅有 Router/Worker；R4 文档和静态 HTML 不能证明 Main 已接入。现有 Session 历史读取和 Instance 级客户端授权也不能直接证明 Router/Worker 观察视图已经满足只读授权要求。这些属于后续接线与验收事实，不要求用户回答。

## 已纠正的方案假设

- 第一轮已确认同一授权工作空间的一条连续 Main 主对话；切换观察页面不建立新 Main，不同隐私范围隔离。
- “Main 不调用任何工具、绝对不能读取执行证据”已被纠正：Main 可以问答、查状态、按需读取有界交付物与证据；实际执行交给 Worker。
- 外部新的人类请求进入所属 Main；合法关联的已有工作跟进与环境事件保持受控直通，必要时给 Main 摘要。
- 结构化问题卡的明确选择可直接交受信核心，核对工作、权限、当前问题后送到原执行；不要求 Main/Router 再改写，观察页不提供写入口。
- Main 暂不可用时，授权工作继续；UI 展示持久状态、结果和待处理事项，明确停止可用；新自然语言输入排队，恢复后补读且不重复派活或送达。
- Worker 自动新增侧栏条目与状态提示，不抢焦点、不自动切页；完成后进入可查历史。
- Main/Router/Worker 默认模型与指令在现有设置页独立配置，可以选择相同模型；不改变正在进行的模型回合，不隐式重跑任务。
- 回复留在原请求信道，桌面 Main 可查看获授权摘要；私人上下文不自动外发到公开 Issue 或群，跨隐私范围另按明确授权。

R4 中的旧档案入口、旧 API 兼容层、旧 profile 共存/回切及完整旧状态迁移，不再属于新产品的目标。已确认产品方向不表示运行代码已实现；工程契约在后续正式规格中综合。

## 设计树与第一轮前沿

| 决定 | 已确认方案 | 确定后解锁的问题 |
|---|---|---|
| Q1：Main 的对话边界 | 同一授权工作空间拥有一条连续主对话；切换查看执行不会建立新 Main；不同私人/团队隐私范围不共享 Main；上下文满后可换代并保持身份与连续性 | Main 持久身份、重连恢复、多窗口与新建对话语义 |
| Q2：Main 可直接做什么 | Main 可沟通、委托、查询状态，并按需读取有界交付物/证据；执行性文件修改、Shell、浏览器操作交给 Worker | 工具允许范围、授权、证据读取预算与上下文压缩 |
| Q3：外部来源如何接入 | 新的人类对话进入所属 Main；既有工作跟进保持受控直通，环境事件由 Router/既有 Worker 处理；Main 收必要摘要 | 来源到 Main/工作映射、跨信道输出与去重 |
| Q4：Main 何时收到工作通知 | 完成、失败、需要人决定及重要方向变化触发有界通知；普通步骤更新只在观察视图，不逐条唤醒 Main | 回传对象、通知合并、摘要预算和交付恢复 |
| Q5：明确停止是否等待模型 | UI 对已明确目标的停止立即调用受信核心命令，随后通知 Main/Router；自然语言歧义需要澄清 | 控制与取消传播、停止按钮、模型不可用时的用户控制 |

第一轮答案：维护者于本轮明确回复“我看了一下 全部按照你的推荐选项”。Q1—Q5 全部确认，后续不再作为未批准问题重问。

## 独立产品边界与工程基线

- 移除的是新产品中的旧架构、入口与兼容代码；不将本决定解释为清空用户磁盘旧数据。本轮不操作用户资料，也不启动旧 ds-bot。
- Q11 的旧配置仅可审阅后提取为角色预设；Q12 的记忆、浏览器与凭据资源仅按预览、归属和明确授权选择导入，不要求完整加载旧产品数据库、Session 历史或维持旧版本兼容。
- 旧派活、未完成工作和历史停止/结果未知状态不能自动变成新的可执行工作；只有新的明确授权工作才走 Main → Router → Worker。
- 新产品从自己的配置、数据和运行入口初始化；不提供旧 profile 选择器、旧客户端/API 兼容 façade、旧工作状态升级或回切旧调度器。需要复用既有内部接缝时可以原位演进，但不承诺对旧产品客户端兼容。
- 保留浏览器、MCP、Office、附件、记忆、日程等已纳入范围的能力及其保护，按新角色/资源重新接入；能力盘点不是把 85 个旧操作原样复活的承诺。
- 发布/升级/恢复面向 DS-SuperAgent 自身的数据与版本，不要求旧 ds-bot archive/activation/reversal 链作为独立产品发布前置。
- Router/Worker 观察只读由服务端授权及公开 DSH 接缝保障；现有通用历史读取不自动获得角色权限。公开接口不足时记录缺口，不修改 DSH。
- 同一委托的重试/恢复使用稳定身份对账，不重复建工作；部分提交与未知结果用既有授权内的持久事实处理，不让用户挑幂等键或私有接口。

Q13 的新决定覆盖 R4 及原方案中的旧产品历史/兼容要求；公开 DSH 接口、数据保护、停止持久性和执行授权继续遵守。后续 to-spec 必须明确替代原规格 D18/D20 的冲突部分，不靠方案页默改正式契约。

## 访谈结论与下一步

三轮产品决定已收敛，无新增产品分叉。下一步将三层角色、三视图、直接控制、来源分流、上下文/隐私边界、可选资源导入和无旧产品兼容综合为正式规格，明确替代 D01/D17/D18/D20 的相关约束，再拆纵向实施票。WorkBrief 字段、幂等键、游标、代次、问题失效检查、配置版本和故障注入等由代理在已定边界内拟定；不再为实现细节延长访谈。本轮完成决议与方案页更新，不创建 GitHub 票或实施产品。
