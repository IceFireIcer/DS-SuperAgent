# 主对话 + 只读运行观察：UI 方案 R3（已被 R4 三层方案取代）

> **已被 [R4 三层运行时与 UI 方案](ui-three-tier-plan.md) 取代。** 本文件保留 R3 的布局与只读观察细节，但“主 Agent 只是 Router 投影”的角色结论作废：维护者已确认主 Agent 是拥有独立模型和上下文的第三个运行时角色。

- 日期：2026-11-14。
- 用户已明确的方向：主 Agent 默认显示且可交互；Router 过程可看但不可交互；Worker Session 自动出现、可看但不可交互；旧 Bot 协作机制逐步退出。UI 本身需要调整，不仅是替换后端机制。
- 本文件记录上述方向、适合现有 UI 的建议及尚需确认的一处角色定义。**本轮不修改产品前端或运行代码，不创建替代 renderer，不删除旧数据或协作代码。**

## 1. 先准确理解“主 Agent”

在产品交互上，本轮已明确有三种可见视图，但不能由此直接推断有三类独立模型运行时：

| 可见入口 | 用户能做什么 | 不能默认推出什么 |
|---|---|---|
| 主 Agent / DS-SuperAgent 主对话 | 默认进入；发送消息、补充要求、回答问题、通过受控入口停止/恢复具体工作 | 不等于旧 Main Bot 的管理员身份；尚不能仅凭名字断言它是第三个独立 LLM Session |
| Router 过程 | 按权限查看已记录的路由输入摘要、决定、关联、工具事实、状态与错误 | 不是另一个可聊天对象，不能向其日志追加提示词或重放路由步骤 |
| Worker 执行 | 工作建立后自动可见；查看任务、步骤、工具、输出、设备/目录、证据和历史 | 不是长期 Bot 联系人，不接受用户直接插话、派活或点击日志卡片驱动工具 |

当前生产工厂配置的是 Router/Worker 两类模型路由（`superagent/src/ds-bot-host.ts:28`、`:84`、`:102`）。核心配置同样只有 Router/Worker 两类角色，角色校验会拒绝第三个角色键；`supervisor-session.ts:50` 的内部监督 Session 仍使用 Router 角色。`engine.ts:519` 的 `conversation(ticketId)` 是 Ticket 数据视图，不是第三个对话 Agent；`engine.ts:1190` 的通用历史读取没有按 Instance/Ticket/角色授权。

**推荐结论**：先把“主 Agent”作为**面向用户的连续协作身份与主对话投影**建模，而不是第三个自治 LLM。主对话展示 Router 的合法人类交互、问题、工作摘要、报告与结果；Router 原始过程另开只读视图。这样三类导航入口来自同一运行体系的三种投影，不引入第二套接单、调度或交付权，也符合原规格 D01“Router 处理人类交互”与 D17“统一对话、按需监督”。

这是当前建议，不是已实现事实。若维护者确实要求“主 Agent”拥有独立于 Router 的模型、上下文或人格，则需在 to-spec 中把它新增为第三个运行时角色，并明确谁负责沟通、研判、交付，输入如何避免双接单，以及取消、升级、故障恢复和读取边界。不能只替换界面标签，也不能把它当作现有核心已具备。

## 2. 推荐布局：继续用原来的壳，重排左侧导航

以下是信息架构线框，不是新 renderer，也不是已批准视觉设计。布局、气泡、卡片、主题、设置和面板继续复用 `ds-bot/src/client/`。

```text
┌───────────────────────┬─────────────────────────────────────────┐
│ DS-SuperAgent         │ 主 Agent / DS-SuperAgent 主对话          │
│                       │                                         │
│ ● 主对话       默认   │ 用户：修复 A，并独立调查 B               │
│                       │ 主 Agent：受理与说明                     │
│ 执行过程              │ [工作 A：修复登录异常] [工作 B：调查性能] │
│   Router        只读  │ [需要你回答的问题 / 交付结果与证据]      │
│                       │                                         │
│ 正在执行 (2)          │                                         │
│   修复登录异常  执行中│                                         │
│   调查性能瓶颈  等待中│                                         │
│                       │                                         │
│ 已完成 / 历史    折叠 │                                         │
│ 旧 Bot / 群历史  过渡 │                                         │
│                       │                                         │
│ 工具与资源 · 设置     │ [消息、附件、语音与受控工作操作]         │
└───────────────────────┴─────────────────────────────────────────┘
```

- “主对话”固定在顶部，承担原来主 Bot 大入口的导航位置，但不继承 Main Bot 的团队治理权限。
- Router 放在“执行过程”而非“Bot 团队”，标记只读；点开后中间区域复用时间线/步骤组件展示路由事实。
- Worker 用工作标题和状态自动生成列表行，例如“修复登录异常”，而不是要求用户新建、命名、拉群后才可执行。
- 建议将同一工作不同 Assignment/Session 代次收在同一工作项下，按需展开；不要重试一次就产生一个看似全新的 Bot 联系人。
- 工具、浏览器、记忆、文件、模型、日程和凭据等能力仍有入口。替换 Bot 协作方式不等于丢弃这些能力。
- 旧 Bot/群入口在过渡期明确区分历史/旧系统，不与新 Worker 混成一张联系人列表。何时冻结和移除日常写入口，仍按能力覆盖和安全切换门执行。

## 3. 三种视图的交互边界

### 主对话：唯一日常沟通入口

- 冷启动默认打开主对话，而非最近出现的 Router/Worker。显式打开的合法只读深链接可例外；具体刷新恢复策略进入规格。
- 主对话显示用户消息、对外确认、问题、工作摘要和交付；Router 的内部调度细节不刷进每一条普通聊天。主对话是产品身份，不自动等于第三个模型角色。
- 用户可从工作卡片明确选择工作，再在主对话补充、停止、恢复或回答；操作必须带合法 Ticket/Attention 等目标，不能按“最近一个 Worker”猜。
- 在只读视图看见问题时，使用“回主对话处理”导航，并保留上下文引用；不自动替用户发送消息或批准。
- 既有附件、语音、图片和结构化卡片继续按相应能力合同接入；不因为主对话统一就降级成纯文本聊天。

### Router：只读过程，不是另一个输入框

- 展示已记录、可授权公开的路由事实：候选为何被接受/忽略、工作如何建立/关联、直通/交回、错误、预算与回执。这里不承诺模型未公开的内部思考全部可读。
- 允许滚动、搜索、复制、展开工具参数/结果和跳到相关工作；这些是阅读操作，不是给 Agent 下指令。
- 不挂载可发送 composer、语音发送、steer、retry/regenerate、执行审批、重放工具或 fork-and-prompt 等写入口。
- 输入框位置显示明确“Router 运行过程 · 只读”，并提供返回主对话；不要仅把发送按钮灰掉而保留隐蔽写路径。
- 当前核心没有按角色/Ticket 授权的通用 Session 观察接口；`getSessionHistory` 只做通用读取。因此不能把 Router 原始 Session 直接挂到客户端并称其安全，需新增受权投影或明确公开接缝。

### Worker：自动发现、按需查看、仍然只读

- 条目由持久工作/Assignment/Session 事实驱动，区分“准备中”和真正运行；不能仅凭模型一句“我启动了 Worker”就制造假执行条目。
- 推荐“自动蹦出来”指左侧自动新增并轻量提示，不弹新窗口、不切走当前视图、不夺键盘焦点。用户点条目后才进入执行详情；此项是交互建议，不把它冒充用户已经指定的弹出方式。
- 页头显示工作标题、只读标记、状态、执行设备/目录及当前代次；详情展示可核查工具事实、输出分页、关键报告和证据。
- 隐藏直接聊天、私信、@派活、修改指令/模型、即时停止/重试、审批和人工问题答复等工作写操作。需要改变工作时回主对话走统一命令入口；应用设置等管理功能不是 Worker 私聊。
- 等待人工、等待设备、stopping、stopped、unknown、ready/ended 分开显示；不得仅用一个“正在思考”动画覆盖所有状态，也不将工作 ended 当作外部消息已送达。
- 工作完成后保留可读历史；重试/换代更新当前执行并保留旧记录，迟到事件不得把列表切回旧代次。

## 4. 自动出现与重连，不只是侧栏动画

1. 先读取授权 Instance 的当前快照与 cursor，再连续补读创建/启动/更新/结束事件；重复或乱序输入按事件身份与执行代次处理。
2. 同一工作同代次只出现一次。新 Assignment/Session 与原 Ticket 关系可追溯，不能依靠扫描所有 DSH Session 后猜哪些是 Worker。
3. 刷新、重连、Host 替换后能重新得到运行条目；不只在创建时发一个瞬时前端通知。
4. 执行中/等待中/已完成按稳定规则分组；状态更新不持续打乱用户正在阅读的条目或滚动位置。
5. 只读视图中的更新不直接触发用户动作。需要人的问题回主对话形成可核对卡片与提醒，不自动切页或替人回答。
6. 窄屏继续使用现有可折叠侧栏/抽屉；一次只显示一个主阅读区，始终可返回主对话。键盘焦点与当前选择可见，状态不能只靠颜色传达。

## 6. 只读必须是协议边界，不是样式开关

- 主对话读模型与内部 Router/Worker 日志分开；读请求按 Instance、工作/来源关系、用户和资源权限过滤，分页与重连也不能越权。
- 声明并校验视图能力：主对话可以提交合法产品命令；Router/Worker 观察视图只能读。前端拿到的只读能力不能用于 prompt、steer、answer、retry、cancel 或修改内部 Session。
- 全局设置与用户工作控制有各自受信入口；“观察视图只读”不等于用户丧失停止工作的权力，而是控制集中到主对话/明确授权的产品动作。
- 检查原生 DSH composer、快捷键、上下文菜单、工具卡、deep link 和普通 Agent mode 等旁路。优先用文档化只读视图/公开授权接缝；接口不足则记录缺口或采用产品自有只读查询投影，绝不 patch DSH。
- 原生日志读取也不自动等于允许向客户端公开全部内容；密钥、私人数据、跨实例资源以及不可公开事件需投影/脱敏。服务端权限检查不能被“知道 Session ID”替代。
- 本轮未实现这些检查；页面里标了只读不代表后台只读已通过验收。管理员通过明确运维权限进行调试另行审计，不把本方案解释成对本机所有高权限工具的 OS 级限制。
- 当前 gateway 的 `read`/`command` 权限粒度是 Instance，不是 UI 视图；同一凭据的写权限不会因打开 Router/Worker 视图自动缩小。角色观察若要求真正的只读隔离，必须新增服务端能力或受权查询投影。

## 7. 旧 Bot 协作逐步退出的 UI 路线

- **先落三视图契约**：主对话默认可交互，Router/Worker 只读，工作动态发现。与共享核心和接线一起做竖切，不等全部后端能力迁完才想 UI。
- **新工作改走统一入口**：新 profile 不再把 Worker 显示成可私聊 Bot；旧消息互派、群 round 与 Main Bot 管理不参与新工作分派。阶段共存时明确消费权，不双派。
- **能力与资源迁入**：保留浏览器/记忆/MCP/Office/日程等价值，重新定义资源和授权，不借“旧 Bot 退出”悄悄共享私有数据或删功能。
- **旧入口收为明确过渡/历史**：只在迁移、权限和历史可读门通过后冻结旧团队写入口；不能仅隐藏按钮就当旧 dispatcher 已退休。
- **最后清理旧机制与 profile**：经过可回退发布窗口后移除已无引用的旧派活、团队/群运行代码和日常入口；档案、回执与迁移报告继续可查。

逐步退出已是本轮用户明确方向，不再当作“是否保留旧 Bot 团队”的开放问题。具体批次、窗口长度、旧菜单如何安置仍需规格化。

## 8. UI 验收从用户操作出发

| 场景 | 应观察到的结果 |
|---|---|
| 首次进入/普通冷启动 | 默认是主对话，有可用输入与能力入口，不落入 Router 或某个旧 Bot 私聊 |
| 发起 A/B 并行工作 | 实际接受/执行事实形成后自动出现工作条目，标题/状态有依据，主对话的输入与焦点不被抢走 |
| 点击 Router / Worker | 明显只读，可读步骤/工具/输出/证据；没有直接下指令、审批、重试或工具重放入口 |
| 构造写请求或走原生 Session 旁路 | 相应产品/会话授权边界拒绝；不能靠去掉前端 disabled 属性恢复交互 |
| 观察时发现需要补充/审批/停止 | 返回主对话并明确工作/问题目标，用户确认后才产生合法命令 |
| 刷新/断线重连/运行代次变化 | 列表重建且不重复，当前/历史执行分开；旧代迟到事件不覆盖新代 |
| Worker 等待、停止、结果未知、完成 | 状态和下一步责任清楚；停止不因重连复活，ended 与送达回执分开 |
| 旧功能与旧历史 | 能力逐项接入；旧 Bot 协作不重新成为接单者；历史和隐私不因新导航而丢失 |
| 窄屏与键盘操作 | 侧栏可收起，阅读/返回路径可达；动态条目不夺焦点，状态带文字，不依赖颜色/动画 |

上述是下一阶段的验收目标，不是当前产品已通过的测试结果。先做现有 UI 内的三视图信息架构与权限契约，再用真实 DSH mock integration/桌面交互证明；静态线框和离线方案图不能替代产品验证。
