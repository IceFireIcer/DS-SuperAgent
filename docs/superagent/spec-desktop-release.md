## Problem Statement

用户要知道桌面版能在哪个平台安装、哪些包已经得到支持，以及把多项工作交给 Main 后如何观察独立 Worker 的排队、执行和交付。维护者也需要区分同一候选是否构建了全部桌面目标，和其中哪些具体安装包已通过验收、可以对外发布。

2026-11-24 架构审计覆盖过多 Worker 和桌面工作流，但代码现状、架构图或其他提交的成功记录都不能证明某个具体构件可以安全发布。

## Solution

每个正式桌面发布候选都从同一提交生成仓库所承诺的多平台包：Windows x64、macOS arm64 与 x64、Linux deb 与 AppImage。每个交付物各有身份与包级证据；只有被单独验收并签核的构件才能列为已支持或发布，并不要求三个系统同时对外发布。

首发是任何用户都可下载的 Windows x64 公开预览，不做内测，不要求邀请或反馈。无项目时用户直接与 Main 对话，Router 和 Worker 不启动。用户在侧边栏创建项目并选择文件夹后，可在单条请求中委托多项独立工作；项目文件夹是工作起点，不是 Worker 的访问硬边界。用户对当前任务明确授权的项目外路径和操作由该任务的 Worker 共享；扩大权限先由 Main 询问，拒绝只取消相关步骤，授权在任务结束时失效。

公开包通过官方 GitHub Releases 分发，显示版本阶段、版本号、提交与支持范围。应用可以自动检查和下载更新，但安装前须获用户确认；安装失败可回退到上一可用版本。更新不得覆盖或删除用户选择的项目文件、用户个人 DSH 数据或已有产品数据；产品数据迁移前提供可恢复备份。

Windows x64 公开预览包用隔离数据完成四项核心验收：无项目首次启动、并行工作分别交付、跨目录授权和拒绝、更新确认和回退。预览可以用明确标注的 mock 验证编排，不能把 mock 当作真实模型证明。稳定版要求同一提交的必需 CI、每个声明支持的包级验收和至少一个声明支持的真实模型端到端流程；维护者签核的对象是明确列出的提交和构件，不是泛称“该版本”。Main 半双工可作为稳定版的已披露限制，但不许静默丢失输入或阻塞其他 Worker。用户反馈自愿，不设置内测或反馈数量门槛。

本规格记录已决定的产品和发布边界，不代表任一候选包通过 CI、测试或获准发布。

## User Stories

1. 作为桌面用户，我希望下载前能看清平台、架构、预览或稳定阶段及支持范围，以便知道手中构件能做什么。
2. 作为第一次打开应用的用户，我希望没有项目时也能直接和 Main 对话，而不被分配一个默认目录或自动启动 Router 和 Worker。
3. 作为项目负责人，我希望在侧边栏主动创建项目并选择本地文件夹，以便决定哪些目录属于我的工作上下文。
4. 作为给 Main 分派工作的人，我希望用一条请求表达多项独立目标，以便无需手动建立或维护长期 Worker 名册。
5. 作为委托多项工作的人，我希望每项工作由独立 Worker 推进，并在并发额度已满时清楚地排队，而不是误以为任务丢失或受“只能有一个 Worker”的限制。
6. 作为等待问题卡答复的人，我希望另一项工作仍能先执行并交付，以便不必等整个工作组结束才使用首个结果。
7. 作为回答问题卡的用户，我希望答复只推进它所属的原 Ticket，不重做已交付的其他 Ticket。
8. 作为项目负责人，我希望需要时可以在当前任务中明确指定项目外文件，以便 Worker 不被项目目录强行限制。
9. 作为授权人，我希望同一任务的多个 Worker 按分工共享明确指定的路径和操作授权，而不因 Worker 轮换而重复询问。
10. 作为授权人，我希望读取权限不被默认为写入权限，且 Worker 需要扩大路径或操作范围时 Main 先征求确认。
11. 作为拒绝额外授权的用户，我希望只取消依赖该权限的步骤，同时让无关的已授权工作继续。
12. 作为用户，我希望跨目录授权在任务结束后失效，以免旧工作许可意外扩展到后续任务。
13. 作为已有个人 DSH 数据的用户，我希望桌面产品只使用自己的产品数据空间，永不写入我的个人 DSH 数据。
14. 作为本地项目负责人，我希望程序更新不删除或回滚我明确选择的项目文件。
15. 作为 macOS 用户，我希望对应架构的独立包通过同一公开发布体系交付，以便不把 Windows 的验收状态误当成 Mac 支持承诺。
16. 作为 Linux 用户，我希望能辨认适用于自己交付形态的 deb 或 AppImage 包，以便按发行渠道选择可安装的候选。
17. 作为 Windows x64 预览用户，我希望公开获取包而不需要邀请码或参加内测，并知道这还不是稳定版承诺。
18. 作为更新用户，我希望应用可以自动检查和下载更新，但只在我确认安装之后改变当前版本。
19. 作为更新失败的用户，我希望回退到上一可用版本，并在数据迁移前能够恢复备份。
20. 作为发布负责人，我希望从同一候选提交记录所有平台及每种实际分发形态的包身份，以便查明下载者拿到的是哪个已审核构件。
21. 作为稳定版用户，我希望只看到已由对应平台候选包证据支持的兼容与支持声明。
22. 作为稳定版维护者，我希望真实模型端到端证据和 mock 编排证据分开报告，以便自动化 mock 成功不冒充真实模型可用。
23. 作为 Main 的用户，我希望知道回复期间何时可以继续输入，且输入不会被静默丢弃，即使 Main 正在回复，其他 Worker 仍可以推进。
24. 作为自愿提供问题报告的用户，我希望只需提供可复现、已脱敏的最小证据，不必提交凭据、完整对话库或产品数据库。
25. 作为维护者，我希望必需 CI、失败、缺证和已知限制都与准确的提交及包摘要关联，以便签核时能做明确的 Go/No-Go 判断。

## Implementation Decisions

- **候选平台矩阵。** 每个正式发布候选都从同一提交生成 Windows x64、macOS arm64 与 x64 ZIP、Linux deb 与 AppImage 的候选构件。平台及分发形态以仓库当前发版清单为准；不能通过省略失败的平台 job 宣称矩阵成功。候选阶段完成多平台构建不要求所有平台在同一天发布。
- **构建不等于支持。** 对外支持声明和 Release 发布以每个实际分发构件的包级证据及维护者签核为准。Windows x64 已有明确的公开预览验收契约；Windows 结果不代替 Mac 或 Linux 构件验收。
- **用户项目与权限。** 不自动创建项目或默认工作目录。没有项目时只运行 Main 对话；用户显式在侧边栏创建项目并指定本地目录后，Router 和 Worker 才能处理该项目工作。项目路径是默认工作上下文而非 Worker 不可越过的边界。当前任务明确指定的路径和操作授权可由参与该任务的 Worker 共享；读取不授权写入，扩权由 Main 先询问，拒绝时只停依赖步骤，任务结束撤销授权。
- **委托身份与并发。** Main 对用户负责，Router 管理 work brief 并拆分独立 Ticket，再为各项授权工作建立执行安排并分派 Worker。某 Ticket 同时只有一个有效 Assignment，不等于系统只能运行一个 Worker。独立工作可在并发预算内重叠，槽满后的普通工作进入可见队列；不承诺无限并发，不改已有并发模型。
- **保留产品入口。** 从现有桌面 Main 历史、工作卡、问题卡和交付流程操作。使用已有产品协议及 DSH 的公开接口，不增加替代 renderer、第二聊天入口、全新调度器、测试专用产品接口或 DSH 私有补丁。停止 Main 回复和停止某项工作保持不同操作。
- **分发和更新。** 官方 GitHub Releases 是公开下载渠道。用户可识别预览或稳定阶段、版本、候选提交、平台、架构和被签核构件。可自动检查并下载更新；未经用户确认不得安装。失败时可回退到上一可用版本。应用数据与项目目录在迁移/更新故障后均有明确恢复边界；不写入个人 DSH 数据。
- **预览门槛。** 对隔离数据中的 Windows x64 候选包，维护者须审核并签署：无项目时 Main-only 首次启动；用户建项目后双独立 Worker 执行重叠，其中一个等待用户答复时另一个先交付，答复后原 Ticket 交付；项目外读取、写入需单独授权以及拒绝不影响无关步骤；更新未确认不安装、失败可回退并保护项目及 DSH 数据。只有两张工作卡不构成并行证据。
- **稳定版门槛。** 同一候选 SHA 的全部必需 CI 通过。每个对外声明支持的 Windows、Mac 或 Linux 分发构件，都须有其构件摘要和该包上的核心流程证据；至少一个声明支持的真实模型须从桌面请求走到核验交付。Mock 不能替代真实模型。改动 SHA 后重新验收；相同 SHA 重新打包后对新构件重新跑包级检查并签核。维护者仅对记录中的特定 SHA 与构件放行。
- **已知限制与拒绝规则。** Main 半双工可在预览和稳定版中按既定条件披露：用户输入不丢失，其他 Worker 不被阻塞。越权、数据丢失、未经确认安装、无法恢复更新、核心流程失效、必需检查失败或缺证，一律 No-Go。仅影响有界、已披露并有可行绕行方案的轻微问题可接受。外部用户反馈自愿，按影响分类，不以用户数、试用时长或反馈数量作为发布条件。
- **签核证据。** 构建与放行分为两份逻辑清晰的记录。构建记录列出同一提交 SHA、各目标架构和所有产物 SHA-256。逐包放行记录关联必需 CI、候选包外部行为结果、模型类型、已知限制及未覆盖环境；不得包含密钥、凭据、完整用户数据或个人目录。

## Testing Decisions

合格的测试要走用户可见的产品入口，在实际候选桌面包上观察 Main、Router、Worker、工作卡和交付结果；每项证据都与确切提交、平台、架构及安装包摘要绑定。多个 Worker 必须有执行重叠的证据，仅看到多个 Ticket 或最终都完成不够。所有本地测试使用隔离的产品数据和工作目录，绝不探测或写入用户的个人 DSH 数据。

最高且首选的产品验收 seam 是启动实际平台候选包，经 Main 发出工作并在原对话观察独立交付；已有的 profile、产品 API、工作目录、执行、升级、备份和 package 测试用于在打包前定位问题，但不能替代下载候选包的端到端证据。本规格定的是后续验收办法，本轮不执行任何构建、测试或发布签核。

| 验收对象 | 外部行为与通过依据 | 代码库中可复用的测试先例 |
| --- | --- | --- |
| 桌面候选构建矩阵 | 同一 SHA 产出 Windows x64、macOS arm64 与 x64 ZIP、Linux deb 与 AppImage。对每个实际交付物记录架构和 SHA-256；必需平台构建失败或缺包即候选矩阵不通过。 | 当前平台发版清单及桌面 package 构建检查。 |
| Windows x64 公开预览包 | 使用隔离数据从实际包启动；无项目时只有 Main。建项目后有重叠的两个独立 Worker，等答与已交付工作互不阻塞且分别在原对话交付。核查明确的跨目录权限、用户拒绝、更新确认、失败回退、备份恢复及个人 DSH 数据保持不变。 | 产品 profile 和桌面 package 检查；产品 API、工作目录、工作执行、Main/工作卡交付测试；桌面 first-run、update prompt、updates、backups 测试。 |
| 每个声明支持的构件 | 在与待发布操作系统和实际架构相匹配的桌面包上重复其包级核心工作流；核对应用启动、数据隔离、更新与平台交付功能。只给通过该构件检查并被维护者签核的包标记为支持。 | 仓库 macOS arm64/x64 和 Linux deb/AppImage 安装、启动、更新的既有发布清单。 |
| 稳定版真实模型流程 | 至少一个声明支持的真实模型在已签核候选包上从 Main 收到工作请求，经 Router 派给 Worker，并将可核验结果交回用户。真实模型名称/类型和覆盖边界与 mock 结果分列。 | 已有产品 profile、Router/Worker 执行与真实模型适配测试；实际包的真实模型记录作为更高层证据。 |

本次规格工作没有运行测试，不能把既有测试文件、旧提交的测试结果、包的源码构建或本地的通过记录当成某个待发布构件的验收结论。对公开预览，mock 可证明桌面对话与编排场景，但发布说明不得称真实模型已通过；稳定版的真实模型门槛不可用 mock 抵消。

## Out of Scope

- 本规格不执行发布验收、平台构建、产品改动、招募内测、打版本标签或向 Releases 上传文件；也不签核任何候选。
- 移动、外部 IM、邮件、远端设备、托管服务或未来的桌面平台/架构不因本次 Windows/macOS/Linux 构建矩阵而获得支持承诺；未来扩展须先定义目标包、用户支持范围和独立验收。
- 不重建或更换现有多 Worker 产品机制，不增加默认项目、默认工作目录、第二套聊天前端，也不要求 Main 全双工。
- 不触及用户的个人 DSH 配置和资料，不开发删除旧版数据或跨产品资料兼容升级的路径。
