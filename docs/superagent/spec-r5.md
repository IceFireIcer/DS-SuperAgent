- 日期：2026-11-14。
- 状态：**正式规格；综合维护者已确认的 Q1—Q14，并替代原规格 D01、D17、D18、D20 中与这些决定冲突的要求。**
- 依据：R5 决定记录 `docs/superagent/product-unification/decision-frontier.md`、ADR 0001、ADR 0002、R5 三层方案，以及原 v2.1 规格 `docs/superagent/spec.md`。
- 替代关系：本规格显式替代原规格 D01、D17、D18、D20 中与新决定冲突的条款；其余 D02—D16、D19 的领域、恢复、来源、执行与交接约束继续有效，除非与本规格直接冲突。
- 产品边界：新产品只采用 Main → Router → Worker；复用现有 UI 组件和公开 DSH API；不保留旧 Bot 架构、旧协作历史入口或旧 ds-bot 产品/协议/状态兼容义务。Q11/Q12 的可审阅配置提取与显式资源导入仍保留。

## Problem Statement

用户需要一个持续存在、可以直接交流的协作者，而不是一套要求用户自己管理联系人、群聊、派活树和底层 Session 的团队工具。当前 DS Bot 以长期 Bot 身份、私聊和群轮次组织工作；这些入口把“谁在聊天”“谁在执行”“哪段历史可查”混在一起，用户要承担选择会话、搬运上下文、追踪后台工作和判断旧系统兼容性的成本。

现有产品已有浏览器、MCP、Office、附件、记忆、日程、来源接入、远端执行、托管 Host 和故障恢复等有价值的能力。新产品不能为了替换协作架构而丢掉这些能力，也不能继续把旧 Bot 的长期身份、Main Bot 管理权、群 relay/round、旧历史入口和旧客户端协议一起带进新核心。

## Solution

DS-SuperAgent 是一个独立产品，使用 Main、Router、Worker 三层角色和现有前端组件：

- **Main** 面向用户，拥有独立模型配置和连续上下文。它负责沟通、澄清、委托、查询状态和按需读取有界证据，不直接修改文件、运行 Shell 或操作浏览器。
- **Router** 接收 Main 的 WorkBrief，负责分解、关联、建立 Ticket/Assignment、分派 Worker、协调跨工作事实，并向 Main 回传有界摘要、关键问题和结果。
- **Worker** 在隔离 Session 中执行一项授权工作，读取原始证据，使用本工作的工具与 Environment，并向 Router 报告；它可以在工作内部使用子代理，但不能直接对用户聊天、创建新 Ticket 或扩大授权。

产品继续复用现有聊天、侧栏、卡片、设置、主题和面板组件：主对话默认可交互；Router 过程只读；Worker 执行自动出现、只读、不抢焦点，完成后保留新产品自己的工作历史。旧 Bot 联系人、团队治理、群轮次、旧协作历史入口、旧 profile 选择/回切和旧 API 兼容层从新产品移除。

用户在明确工作上的停止和结构化问题答案可以直达受信核心，不等待 Main 或 Router 推理；输入框“停止生成”只停止 Main 当前回复。Main 模型暂不可用时，已授权工作继续，持久事实仍可查看，新自然语言输入排队，恢复后按稳定身份补读且不重复派工或送达。

## User Stories

1. 作为用户，我希望始终与同一个逻辑 Main 协作，以便不必因为切换查看页面而重新建立对话。
2. 作为用户，我希望在同一授权工作空间内补一句话就能跟进原工作，以便系统不会重复创建同一项任务。
3. 作为用户，我希望 Main 的上下文换代后仍保留身份、授权和未完成事项，以便摘要遗漏时还能补读原始依据。
4. 作为用户，我希望个人与团队隐私范围各自拥有独立 Main，以便一个范围的资料不会自动进入另一个范围。
5. 作为用户，我希望 Main 能回答、澄清、委托和查询状态，以便日常交流不必直接面对执行日志。
6. 作为用户，我希望 Main 只在需要时读取有界交付物或证据，以便主对话不被完整 Worker transcript 占满。
7. 作为用户，我希望一句“修复 A，并独立调查 B”能被分解为两项独立工作，以便并行推进而不伪造两条用户消息。
8. 作为用户，我希望两项独立工作能各自运行、各自完成和各自汇报，以便一项等待不会拖住另一项。
9. 作为用户，我希望 Router 过程只读可查，以便理解工作为何被建立、关联、分派或交回，但不能从日志向 Router 下指令。
10. 作为用户，我希望 Worker 执行只读可查，以便查看工具事实、输出、设备、报告和证据，但不能把 Worker 当第二个聊天入口。
11. 作为用户，我希望真实 Worker 开始时自动出现侧栏条目，以便不需要手动创建或命名执行者。
12. 作为用户，我希望 Worker 自动出现时不弹窗、不切页、不抢焦点，以便我正在写的内容不被打断。
13. 作为用户，我希望完成的 Worker 和每次执行代次保留在可查历史中，以便结果和旧代次都能追溯。
14. 作为用户，我希望只在完成、失败、需要决定或重要方向变化时收到 Main 通知，以便普通步骤不会持续打扰我。
15. 作为用户，我希望结果默认回到原请求信道，以便我知道哪项工作在哪段讨论中被交付。
16. 作为用户，我希望外部来源中的新人类请求进入所属 Main，以便来源不同不会绕开我已确认的交互入口。
17. 作为用户，我希望既有工作的合法跟进直接到原工作，以便不必每次让 Main 重新解释整段背景。
18. 作为用户，我希望 PR、CI、设备和日程等环境事件按归属和订阅直通，以便关键变化能被处理且不扩大权限。
19. 作为用户，我希望私人背景不会因为一次公开回复就自动进入公开 Issue 或群聊，以便跨隐私范围发布必须经过明确授权。
20. 作为用户，我希望 Worker 的问题以主对话中的结构化问题卡呈现，以便问题、选项、所属工作和回答权限都清楚。
21. 作为用户，我希望明确的问题选择可以直接提交给原工作，以便不需要等待 Main 或 Router 再次改写。
22. 作为用户，我希望问题已变化或工作已停止时旧答案被拒绝，以便过期回答不会推进错误工作。
23. 作为用户，我希望输入框“停止生成”只停止 Main 当前回复，以便不误停已经派出的后台工作。
24. 作为用户，我希望在工作卡上停止明确的工作，以便停止对象、范围、持久状态和取消传播都可核查。
25. 作为用户，如果产品提供“全部停止”，我希望它单独标明范围，以便不会把局部停止误认为全局停止。
26. 作为用户，我希望 Main 模型暂不可用时已授权工作继续，以便界面故障不变成工作故障。
27. 作为用户，我希望 Main 暂不可用时新自然语言输入排队，以便恢复后不会丢失或重复处理。
28. 作为用户，我希望 Main 恢复后按稳定输入和工作身份补读，以便不重复建立工作、不重复送达结果。
29. 作为操作者，我希望在现有设置页分别配置 Main、Router 和 Worker 的模型与指令，以便按角色分配沟通、协调和执行能力。
30. 作为操作者，我希望三层可以选择相同模型，以便独立配置不等于强制购买或选择三个模型产品。
31. 作为操作者，我希望保存角色配置只影响后续请求，不改变正在进行的模型回合，以便在途工作保持可预测。
32. 作为操作者，我希望 Agent 不能自行修改角色配置或扩大权限，以便配置入口始终是用户授权动作。
33. 作为操作者，我希望把旧名称、模型、指令、技能和形象审阅后提取为角色预设，以便复用有价值的配置而不恢复旧 Bot。
34. 作为操作者，我希望预设选择不继承旧 Main Bot 管理权，以便配置复用不等于权限继承。
35. 作为用户，我希望在导入旧记忆、浏览器登录态或凭据前看到归属和范围预览，以便明确选择是否导入以及共享给谁。
36. 作为用户，我希望私有资源不会自动合并到 Main 或全局，以便新产品初始化不会泄露旧资料。
37. 作为用户，我希望不导入旧资源时原件仍保留在磁盘，以便移除旧架构不等于删除我的资料。
38. 作为用户，我希望新产品没有旧 Bot、旧群聊或旧团队管理入口，以便不再维护两套协作模型。
39. 作为用户，我希望新产品不提供旧协作历史入口、旧 profile 选择/回切或旧客户端协议兼容，以便产品边界清楚。
40. 作为用户，我希望新产品自己的 Main、Router、Worker、Ticket、结果和执行历史仍可查，以便移除旧架构不删除新工作记录。
41. 作为用户，我希望旧未完成、已停止或结果未知的派活不会自动变成新的可执行队列，以便迁移不会盲目重做。
42. 作为用户，我希望浏览器、MCP、Office、附件、记忆、日程、来源、远端执行和托管能力仍有明确入口，以便协作重构不丢能力。
43. 作为用户，我希望凭据通过受控 vault/reference 使用，以便密钥不进入 prompt、界面投影或日志。
44. 作为用户，我希望结果未知时系统先按原命令或作业身份对账，以便不会把“没有回执”误报为失败并重做。
45. 作为用户，我希望人工停止在重连、重启、设备上线和监督恢复后仍然有效，以便自动机制不能解除我的停止。
46. 作为用户，我希望 Worker 失败或换代时旧代次回调无效，以便迟到结果不会覆盖当前执行。
47. 作为操作者，我希望看到每项工作的实际设备、目录、能力和执行代次，以便核查工作真正在哪里运行。
48. 作为操作者，我希望远端专用工作在没有合格设备时明确等待，以便系统不会偷偷改在本机执行。
49. 作为操作者，我希望常驻 Host 或服务器托管下客户端关闭不停止授权工作，以便界面生命周期不等于工作生命周期。
50. 作为操作者，我希望 Watchdog 自动查证和安全重试，但纠偏或暂停前先提出证据化提案，以便恢复机制不越过我的控制。
51. 作为操作者，我希望来源准入、并发预算、主动规则和健康状态可配置、可核查，以便系统资源不会被无依据工作耗尽。
52. 作为维护者，我希望所有产品行为测试都通过公开 Engine 命令与查询观察，以便测试不绑定私有实现结构。
53. 作为维护者，我希望 DSH Session、来源、信道和设备适配器分别有契约测试，以便外部语义变化能被单独发现。
54. 作为维护者，我希望测试只用 mock 模型、隔离数据、临时目录和空闲端口，以便不接触真实 DSH 数据或凭据。
55. 作为维护者，我希望领域、mock 集成、真实模型、真实信道、Windows 与托管部署证据分开报告，以便部分通过不会被夸大为全量完成。
56. 作为用户，我希望看到确认、发送、失败和永久丢弃的真实回执，以便不会把“已排队”误认为“已送达”。
57. 作为用户，我希望等待人、等待设备、结果未知、停止中和已完成分别显示，以便知道下一步由谁推动。
58. 作为用户，我希望明确的恢复动作重新校验当前授权，以便历史授权不会越过新的限制。
59. 作为用户，我希望只读观察视图通过键盘可浏览、可搜索、可复制，并始终能返回主对话，以便查看过程不妨碍日常操作。
60. 作为用户，我希望界面继续使用现有视觉与动效组件，而不是出现第二套 renderer 或陌生前端，以便产品演进保持连续。
61. 作为维护者，我希望旧 85 个操作有完整处置清单，但不要求新客户端逐接口兼容，以便能力不遗漏而旧协议不复活。
62. 作为维护者，我希望旧架构移除有可核查的入口与消费检查，以便没有旧 dispatcher、群 round 或旧历史入口继续接收输入。

## Implementation Decisions

### R5-D01. 三层角色、职责与工具边界

- 一个 Instance 只有一个逻辑 Main、一个逻辑 Router 和一组按工作隔离的 Worker Session。Main、Router、Worker 各自拥有独立模型 route、Session 与上下文；切换 UI 视图、刷新或重连不创建第二个 Main。
- Main 负责用户沟通、澄清、委托、状态查询和有界证据读取。Main 的工具集是产品级、类型化的委托与查询能力，不包含文件修改、Shell、浏览器操作或直接创建 Ticket/Worker 的能力。
- Router 接收 WorkBrief 和已授权来源事件，负责工作分解、关联、Ticket/Mandate/Assignment 建立、Worker 分派、跨任务事实、handback、汇总与有界回传。Router 不直接与用户聊天，不把 Worker 全量日志塞回 Main，不替 Worker 规划任务内全部步骤。
- Worker 在独立 Session 和本工作 Mandate 内调查、执行和验证，使用本工作 Environment 内的工具；可以在工作内部组织子代理/Agent Team，但不能直接向用户发消息、创建新的工作、修改 Main 配置或自行扩大权限。
- Main/Router/Worker 的模型配置独立，允许选择相同模型。模型配置独立不表示需要三个不同供应商或模型产品。
- Router 与 Worker 的执行过程可由主对话 UI 以只读投影查看；阅读过程不把完整 transcript 自动写入 Main Session。

### R5-D02. 工作协议与稳定身份

产品协议至少包含以下语义对象。字段名和序列化形式可在实施票中按现有公开 Engine 形状收敛，但语义和身份规则不得弱化：

| 对象 | 方向 | 最低语义 |
| --- | --- | --- |
| WorkBrief | Main → Router | 稳定委托 ID、Instance、Main Session/Turn、原始用户依据、目标、约束、验收条件、证据引用、可选多工作意图、配置版本与创建时间 |
| WorkReceipt | Router → Main | 接单或拒绝原因、建立的 Ticket/工作项列表、关联已有工作、需要 Main 知道的下一步、同一 WorkBrief 的重试回执 |
| WorkUpdate | Router → Main | 关键状态或方向变化、责任方、用户可见摘要、工作引用、是否需要人决定；普通步骤不逐条发送 |
| Attention | Router → 主对话问题卡 | 所属工作/问题版本、问题与选项、回答所需权限、是否可自由输入、过期或失效依据 |
| WorkFollowUp | Main → Router | 引用原工作/WorkBrief/Ticket、方向变化、来源依据、目标变化；由 Router 决定直通或重新研判 |
| WorkControl | 主对话/受信 UI → 核心 | 明确目标工作、动作（stop/resume/retry/all-stop）、用户授权、原因、期望版本；不得按“最近 Worker”猜测目标 |
| WorkOutcome | Router → Main | 成功、失败、未知、等待、停止或受阻、交付物引用、可验证证据摘要、下一步可选动作 |

- 同一 WorkBrief、WorkControl、AttentionAnswer 和来源接受命令必须有稳定 command ID 与规范化输入指纹；同 ID 重试复用原回执，同 ID 异文拒绝。
- 一条复合请求只能保留一份不可变原始来源事件。Router 可以把该请求分解成多个工作项，但每个工作项必须有自己的稳定身份、目标、约束、Mandate、订阅和交付条件；不得复制成多条用户消息来伪装分项。
- 分项创建可能部分成功。系统必须记录已建立与未建立的工作项；重试只承接原决定并补齐缺项，不得重复派发已存在工作。目标发生变化时显式冲突或重新决定。
- WorkBrief 不是用户原文的替代。Router 和 Worker 必须保留并可读取原始来源事件；Main 的摘要是导航，不是事实替代品。
- 同一工作按 WorkBrief/Ticket/Assignment/消息身份去重；刷新、网络重试、模型重复建议和重启不能创建同一批工作或重复送达。
- WorkUpdate、Attention 和 WorkOutcome 不携带完整 Worker transcript、逐条工具输出、Shell 日志或大段 diff；需要核查时使用有界证据引用和分页读取。

### R5-D03. Main 的连续对话与上下文预算

- 同一授权工作空间拥有一条连续 Main 主对话。UI Session、窗口或观察页面不是 Main 身份；多个窗口和重连可以附着到同一个逻辑 Main。
- 不同隐私范围使用不同 Instance 和 Main；一个 Instance 的对话、证据、资源、工作索引和来源不进入另一个 Instance。
- Main 上下文包含用户消息、用户可见回复、自己的 WorkBrief 回执、工作索引、关键 WorkUpdate、Attention、WorkOutcome，以及用户主动要求核查时的受权有界证据。
- Main 默认不接收 Worker 逐条 tool call、tool output、Shell 输出、完整 diff、测试日志、Router 内部批处理全文或其他 Instance 的私密数据。
- 上下文满后允许 Main Session 换代。换代必须保留逻辑 Main 身份、目标、约束、未处理输入、工作索引和关键证据引用；新 Session 不能丢失主对话连续性或重复接受旧输入。
- Main 失败与 Router/Worker 工作失败分开表示。Main 模型不可用时，持久工作事实、结果、问题卡和明确停止仍可由受信核心提供；新自然语言输入持久排队，恢复后按稳定身份补读。
- Main 的回复留在原请求信道；桌面 Main 可查看获授权摘要和关联。私人上下文不自动进入公开 Issue、群聊或其他隐私范围。

### R5-D04. Router 协调与 Worker 隔离

- Router 接收 WorkBrief 后负责把工作分解为一项或多项 Ticket；不要求 Main 先替 Router 拆分，也不要求用户确认每一项内部 Ticket。
- Router 为每个 Ticket 建立或关联 Mandate/Assignment，选择符合授权和 Environment 条件的 Worker Session；Worker 只读取本工作需要的原始依据、约束、证据和资源。
- 已有 owner 的合法跟进、环境事件和跨任务事实按归属直通 Router/Worker；普通步骤留在观察视图，不逐条唤醒 Main。
- Worker 遇到范围外要求时 handback，由 Router 重新研判；不能把任意主题塞入原工作，也不能通过 Worker 间的自由对话绕过授权。
- 同一 Ticket 同时最多一个有效 Assignment。Assignment 可换代，Session 可复用或显式换代；旧代迟到回调只能审计，不能改变当前工作状态。
- Worker 条目由真实 Ticket/Assignment/Session 事实驱动，不由模型一句“我启动了 Worker”生成，也不按每个 UI Session 创建一个“新 Bot”。
- 工作完成、失败、等待人、等待设备、停止中和结果未知必须分别呈现；一个“正在思考”动画不能覆盖所有状态。

### R5-D05. 来源、交付与隐私边界

- 来源事件先持久化并核查 scope、来源实例、发送者和归属。外部新的人类请求进入所属 Main，由 Main 理解后委托 Router；不因来源来自 GitHub、飞书或其他平台就绕开 Main。
- 已合法关联的既有工作跟进、PR/CI/设备事件和日程 occurrence 可按订阅与归属受控直通原工作或 Router；不先把全文塞进 Main。
- Main 只收到必要的关键变化摘要。普通 progress 留在内部观察视图；完成、失败、需要人决定和重要方向变化才形成有界通知。
- 结果默认回到工作发起信道。跨信道更新只有在来源身份、目标可访问性、同 Instance 和明确授权均核验后才可改变交付位置；仅收到新事件不自动广播或复制其他信道内容。
- 发送用途区分 acknowledgement、answer、result、attention；Attention 必须匹配当前结构化问题，answer 必须对应原始问题，result 必须对应当前 ready/ended 结果。
- Outbox 回执区分 pending、sent、dropped。平台已收到而响应丢失的窗口按信道幂等键、marker 或查询对账处理；pending 不得宣称已送达，dropped 不得自动改投其他对象。

### R5-D06. 用户直接控制与失败语义

- 输入框“停止生成”只取消 Main 当前回复。它不自动停止已提交或已派出的工作；如果 WorkBrief 的提交结果未知，按原稳定身份对账，不用停止回复来猜测委托未提交。
- 工作卡上的“停止工作”必须携带明确 Ticket/工作项和用户授权，直接调用受信核心持久记录停止、传播取消，再通知 Main/Router；不等待 Main 或 Router 推理。
- 自然语言中的停止若目标有歧义，先澄清；不得按“最近一个 Worker”或当前打开视图猜目标。
- 如产品提供“全部停止”，必须单独标明范围、影响和不可自动恢复的语义；不能把它混同为输入框停止生成。
- 结构化问题卡上的明确选择可以直接提交受信核心。核心校验工作、Instance、用户权限、当前问题版本和停止/等待约束后，把答案送到原执行；过期或已变更问题拒绝旧答复。
- 问题卡答案不要求 Main 或 Router 改写；Main/Router 只接收事实通知。观察视图不提供回答输入，用户必须回到主对话或明确的产品控制卡片。
- 人工停止是持久约束；重连、重启、Host 接管、设备上线、CI、普通跟进和监督动作不能自动解除。只有用户明确恢复才可创建新 Assignment，并重新核验授权。
- 外部结果未知时保留 unknown，按原 command/job/outbox 身份查证；只阻塞受影响操作与依赖，无关工作继续。没有证据时不能伪报成功或失败，也不能换设备盲重做。

### R5-D07. UI 三视图与现有组件复用

- 产品继续使用现有聊天、侧栏、卡片、设置、主题、面板和输入组件；不创建替代 renderer、第二套桌面壳或独立视觉语言。
- 主对话默认显示、唯一日常输入区，承担用户消息、Main 回复、工作摘要、问题卡、确认、结果和证据入口。
- Router 过程是只读视图，展示已记录的 WorkBrief 接收、分解、Ticket/Assignment、关联/拒绝/交回、状态、错误、预算和回执；不提供 composer、steer、retry、regenerate、审批、工具重放、fork-and-prompt 或其他写入口。
- Worker 执行是只读视图，展示工作标题、状态、只读标记、设备/目录、代次、工具事实、输出分页、报告和证据；不提供私聊、@派活、修改指令/模型、审批、停复或问题回答。
- Worker 开始后自动新增侧栏条目和轻量状态提示，不弹窗、不自动切页、不抢键盘焦点；用户主动点击才进入详情。刷新、重连和 Host 替换后按工作身份重建，不能重复或把旧代次切回当前。
- 只读不是 CSS 隐藏或禁用按钮，而是服务端角色/工作授权投影。前端拿到的只读能力不能用于 prompt、steer、answer、retry、cancel 或修改内部 Session；知道 Session ID 不等于获得读取权限。
- 观察视图中的问题提供“回主对话处理”导航并保留工作/问题引用；不在只读区替用户发送、批准或重试。
- 现有 UI 设计标准中的视觉、动效、键盘与可访问性规则继续适用；用户可见术语需在 UI 实施时从旧 Bot/Main Bot/群语义更新为 Main/Router/Worker/工作，不能静默保留旧称呼。

### R5-D08. 角色配置、版本与角色预设

- 角色配置包含 main、router、worker 三个 role profile，每个至少包含名称、模型 route、指令和技能；三层可以引用相同模型。
- 配置保存基于明确 revision，冲突拒绝且保留草稿；保存形成新版本，正在进行的模型回合继续原版本，后续合法请求才使用新配置，不取消、重建或重跑已有工作。
- 每次模型请求记录所用角色配置版本；查询可追溯某 Session 使用了哪个 revision 和哪些角色 route。Agent 不能自行修改角色配置。
- 角色预设是可审阅的配置模板，不是长期 Bot 或额外 Main。预设可以来自旧名称、模型、指令、技能和形象，但选择预设是用户明确动作，不授予旧 Main Bot 管理权、资源权限或历史工作。
- 预设与实时角色配置分离；应用预设形成新的角色配置 revision，并沿用相同的冲突与在途回合规则。

### R5-D09. 新产品初始化与可选资源导入

- 新产品从自己的配置、数据目录和运行入口初始化，不自动加载旧产品数据库、旧 Session 历史、旧工作队列或旧 dispatcher。
- 旧配置提取为角色预设属于可选初始化：先展示名称、模型、指令、技能和形象的来源与目标，再由用户选择；不自动创建长期 Bot、额外 Main 或旧权限。
- 旧记忆、浏览器登录态、工作目录和 credential grants 可选导入：先预览归属、隐私范围、目标角色/工作空间/Environment 和共享范围，再由用户明确选择；不自动合并到 Main 或全局资源。
- 导入读取旧资料的副本或明确导出，不写用户自己的 DSH 数据或旧产品数据目录。未导入的资料不删除，也不因移除旧架构而被清空。
- Secret 只经受控 vault/reference 使用，不进入 prompt、manifest、界面投影或日志。导入的旧凭据必须重新建立明确授权，不继承旧 Bot 或旧 Main Bot 的权限。
- 不导入旧 in-flight、stopped 或 unknown 工作为新的可执行队列。旧派活不自动重放；任何承接都需要新工作身份、当前授权和新的明确请求。
- 导入失败、取消和重复执行必须可恢复：同一批次重试不得重复创建资源，冲突必须让用户选择或保持未导入状态。

### R5-D10. 旧 Bot 架构移除与新产品历史

- 新产品的产品模型只包含 Main、Router、Worker、Ticket、Assignment、Session、来源与资源；不保留长期 Bot 联系人、Bot 私聊派活、Bot 互派、旧内部群 relay/round、Main Bot 治理或团队管理入口。
- 新产品不提供旧协作历史入口、旧 profile 选择/回切、旧客户端/API 兼容 façade、旧状态模型兼容或旧核心调度回切。
- 移除旧架构不是删除用户磁盘上的旧资料，也不是把旧产品改名为新产品的运行时模式。旧产品与新产品是不同产品，旧数据由旧产品保留。
- 新产品自己的主对话、Router 协调、Worker 执行、结果、回执和代次历史必须可查；完成工作留在历史中，重试/换代保留旧记录。
- 旧 85 个 HTTP 操作和 API 外能力继续作为处置清单：保留能力按新协议接入，语义变化项按新工作验收，旧机制删除；不以逐接口兼容作为完成标准，也不因删除旧 API 而丢弃已要求的能力。
- 浏览器、MCP、Office、附件、记忆、日程、来源、远端执行、托管 Host、Watchdog 与监督能力按新角色和资源授权接入；其保护、失败状态、停止、未知结果和回显继续有效。

### R5-D11. 独立产品 profile、DSH 接缝与公开 API

- 新产品使用自己的独立产品 profile、DSH_HOME、业务数据库和 Session 数据；不读取或写入用户自己的 DSH 数据、旧产品数据目录或测试外账号。
- 只通过公开 DSH 入口装配，包括 `@deepseek-ai/dsh/profile-boot`、`dsh-app-boot`、bundle patch 和客户端 `dsh.client` 清单；不修改 DSH 安装、不依赖安装内部文件、不增加 DSH 源码补丁。
- 新产品只提供一个产品运行入口和一条产品 profile 路径；不提供旧/新 profile 选择器或回切旧核心的运行时模式。旧产品仍是独立产品，不作为新产品的兼容模式。
- 复用现有 UI 组件不等于复用旧 Bot 领域模型。UI 组件通过新产品命令/查询投影接入；不得自动启动旧 roster、群 dispatcher、Bot 工具或旧 `/api/bot` 兼容路由。
- 固定 DSH 版本并保留公开 API 兼容检查。DSH 升级先运行产品 profile 启动和无密钥 mock 消息 smoke，再运行相关 UI/插件回归；新增内部深路径导入即失败。
- 生成的前端资产继续由现有构建流程生成，不手工编辑生成物；仓库的 UI 边界检查和既有生成一致性检查继续适用。

### R5-D12. 持久化、恢复、授权与故障边界

- Domain Engine 仍是唯一领域写入口。业务状态、输入归属、配置版本、Effects/Outbox 与命令回执在同一业务事务提交；模型、网络、设备与外发在提交后派发。
- 本机业务基线 SQLite，共享服务器业务后端 PostgreSQL；DSH Session 使用公开 SessionPersistence/SessionHandle 与独立 Session 后端。业务库与 Session 库分别恢复，不宣称跨库 ACID。
- 同 Instance 写命令串行化；命令按 Instance、稳定 command ID 和规范化输入指纹去重。COMMIT/连接结果未知时按原 ID 开新事务、重新取得同 Instance 锁并查询原回执，不换 ID 盲试。
- Host epoch/fencing、Assignment 代次、Session writer epoch 和 Environment incarnation 共同约束写权；旧代事实只能审计，不能改变当前状态。人工停止、暂停、等待人工和撤权优先于自动恢复。
- 只读查询按 Instance、角色、Ticket、来源关系和资源授权过滤。通用 `getSessionHistory` 只证明存在通用读取接缝，不能直接暴露给 Router/Worker 观察视图；必须新增角色/工作感知的投影或在产品层建立同等服务端检查。
- 当前 NativeSessions/RoleConfig 只有 Router/Worker；本规格要求新增 Main 角色、Main Session 与工作协议。不能把 Main 作为 Router 的 UI 标签或提示词别名。
- 恢复不承诺半个模型 turn、Shell、PTY 或设备命令从原执行点续跑；恢复依赖持久事实、原身份和现实对账。

### R5-D13. 能力保留与执行环境

- 每个有效 Assignment 绑定一个明确 Environment，使用配套 fs/subprocess/job 能力和独立 scope；文件读写、搜索、Shell/PTY、输出和取消属于同一执行世界。
- Worker 及其子代理继承本工作的 Environment、权限、资源 scope 和生命周期；不同 Worker 或不同 Ticket 不串线。
- 设备断连不表示作业停止；重连按 incarnation 和稳定 job ID 对账。停止只有确认同一 managed range 实际静止后才可报告 cancelled。
- 本地、远端、auto 目标选择按现有授权和 Environment 条件解析，记录设备、目录、能力与选择依据；remote-only 无合格目标时等待或受阻，不静默回退本机。
- 浏览器、MCP、Office、附件、记忆、日程、来源、远端执行、托管 Host、Watchdog 与 Supervisor 继续保留；各自声明运行位置、数据归属、授权、停止、失败和回显。
- 旧团队工具中的 `message_bot`、`create_bot`、`create_group`、`group_relay` 等旧派活/群机制不作为新产品工具；`ask_user` 以 Attention 替代，记忆/浏览器/能力管理按新资源授权接入。

### R5-D14. 对原规格 D01、D17、D18、D20 的显式替代

| 原决定 | 需要替代的约束 | 本规格的替代 |
| --- | --- | --- |

## Testing Decisions

### 测试原则与主张

- 好测试只断言外部可观察行为：用户输入、公开命令、持久状态、查询结果、工作状态、角色、Session 身份、Outbox 回执、错误与恢复事实。测试不依赖私有 helper、内部类数量、调用顺序或某段提示词文本。
- 所有产品行为优先从最高 seam 进入：**Domain Engine 的公开产品命令与查询**。现有 `submit`、来源接受、`answerAttention`、`stopTicket`、`resumeTicket`、`getTicket`、`conversation`、`getSupervision` 等公开接缝可以复用形状，但必须扩展为 Main 绑定、WorkBrief/Receipt/Outcome、角色配置和角色感知只读投影。
- 新增的主 seam 是同一公开 Engine 产品接口上的“角色/工作感知只读投影”；不另开一个 UI 专用产品写入口，也不把通用 Session 读取当观察 API。
- DSH NativeSessions、来源/Channel、Environment 和设备执行只做契约测试；它们是产品 seam 依赖的外部系统，不是替代产品 seam。测试替换这些适配器时，必须验证真实会变化的语义，不用大量内部 mock 代替核心行为。
- 只读权限必须在服务端断言，不能只断言前端按钮不存在。负对照包括：知道 Session ID、构造只读视图请求、直接调用 prompt/steer/retry/cancel、跨 Instance 猜 Ticket、过期 Attention、停止后自动恢复。
- 测试使用 mock 模型、隔离临时目录、独立 SQLite、空闲端口和虚构来源数据；不读取用户自己的 `~/.dsh`、旧产品数据、真实账号或密钥。启动的服务、Host、端口和进程必须关闭。
- 真实模型、真实 GitHub/飞书、真实设备、Windows 原生和托管部署属于分层证据，单独报告；mock 通过不能替代这些层，静态 HTML 方案页不能替代产品运行。

### 建议的测试 seam

| Seam | 现有/新增 | 测试内容 | 为什么在最高层 |
| --- | --- | --- | --- |
| Domain Engine 公开命令与查询 | 现有，主 seam | 用户输入、WorkBrief、Ticket/Assignment、Worker 结果、停止/回答、恢复、Outbox、角色配置、查询投影 | 用产品语义断言，不绑定实现结构；现有 Engine 测试已按此方式使用 |
| 角色/工作感知只读投影 | 新增，属于同一产品接口 | Router/Worker 观察视图、跨 Instance/Ticket 拒绝、分页和引用不越权、旧代次不可写 | 只读是协议边界；必须在服务端拒绝写和越权读 |
| DSH NativeSessions 契约 | 现有 | Main/Router/Worker 三种 role、Session 创建/恢复、模型 route、指令、flush、取消、换代、持久序列 | 验证真实 DSH 公开接缝；但不由它决定产品工作状态 |
| 来源/Channel/Delivery 契约 | 现有 | 来源身份、版本/删除、权限、消息用途、幂等发送、回执、跨隐私目标 | 验证外部平台语义与产品交付边界 |
| Environment/设备执行契约 | 现有 | 文件/搜索/命令同一执行世界、子代理继承、取消范围、断连对账、远端等待 | 验证执行世界与授权，不把设备适配器当领域核心 |
| UI/客户端命令入口 | 现有 | 认证、Instance 授权、命令/读取能力、撤销、重连补读、主对话/观察视图能力 | 现有 client-gateway 已有先例；新增角色视图权限在此层断言 |

以上 seam 是本次规格准备的核心审阅点。若审阅不接受“角色/工作感知只读投影”作为 Engine 产品接口的一部分，就应在 `/to-spec` 发布前先修正 seam，而不是把通用 Session 读取直接暴露给客户端。

### 既有测试先例

- Engine 命令与 mock 模型：现有 `superagent/test/execution.test.mjs` 通过公开 Engine 接受、执行、查询与恢复；适合扩展 Main/Router/Worker 多角色和复合分项场景。

### UI 与真实环境验收边界

- 领域和 mock 测试证明协议、身份、权限和恢复语义，不证明真实界面可用。

## Further Notes

### 决定来源与效力

本规格综合的是维护者已确认的 Q1—Q14，不重新访谈。Main 独立于 Router、三层角色和三视图、Worker 自动出现、直接控制、Main 故障继续工作、角色配置、跨隐私交付、可选配置/资源导入、移除旧 Bot 架构均已有明确答案。协议字段、幂等键、游标、代次、问题失效检查、配置版本和故障注入是工程收敛建议，不是新增产品分叉。

### 确认的产品与测试边界

- 主测试 seam 是“Engine 公开产品命令与查询”，角色/工作感知只读投影作为同一产品接口的扩展；通用 Session 读取不直接暴露成观察 API。
- D01/D17/D18/D20 的替代表覆盖原规格冲突；D02—D16、D19 中未被替代的保护继续有效。
- 新产品使用单一独立运行入口，不保留旧/新 profile 选择；复用现有 UI 组件不等于保留旧 Bot 领域模型或旧协议。
- 旧 85 操作是能力处置清单，不要求逐接口兼容；保留能力与旧机制删除分别验收。

### 进入实施票前的工程收敛

以下项目应在 `/to-tickets` 或实施票中确定，不需要重新打开产品访谈：
